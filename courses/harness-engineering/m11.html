Evolving the harness: steering, entropy and new models

A harness is never finished. Agents copy the patterns they find, so a codebase drifts unless something pushes back. Every new model shifts which scaffolding helps and which just costs tokens. This module covers how to run the harness as a living system: who maintains it, how it's cleaned, and how to decide what to remove.

By the end of this module you can

  • Run the steering loop that turns recurring failures into harness changes.
  • Fight entropy with encoded principles and background cleanup agents.
  • Re-evaluate a harness when the model changes, and remove components safely.
  • Document each harness component with its reason to exist and its removal test.

The steering loop

Böckeler describes the human's job in a harnessed system as steering: iterating on the harness itself. When the same issue appears more than once, improve a guide or a sensor so that it becomes less likely or impossible. Agents can do much of that work, such as drafting a structural test or scaffolding a custom linter, so the loop gets cheaper as it runs.

OpenAI's Codex team ran the same loop with one more rule: when docs weren't enough to change the agent's behavior, they promoted the rule into code (a lint, a test, a structural check). Human taste was captured in docs or tooling rather than in individual review comments.

Entropy: agents copy what they see

Agents imitate existing patterns, including bad ones, so every shortcut that lands becomes a template for the next change. OpenAI's team initially fought this with a weekly manual cleanup that took about a fifth of the team's time, and it didn't scale. What replaced it:

  • Golden principles written into the repo as opinionated, mechanical rules, for example preferring shared utility packages to hand-rolled helpers, and validating data shapes rather than guessing at them.
  • Background cleanup agents on a schedule that scan for deviations, update per-domain quality grades, and open small refactoring PRs. Most can be reviewed in under a minute and merged automatically.
  • A doc-gardening agent that finds documentation that no longer matches the code and opens fix-up PRs.

Their framing of technical debt is worth borrowing: a high-interest loan that should be paid down continuously in small increments rather than in occasional large refactors.

Throughput changes the merge policy

With agents producing far more change than humans can review, OpenAI kept blocking gates minimal and pull requests short-lived. Flaky tests were usually re-run rather than allowed to block. Their reasoning: when throughput vastly exceeds human attention, correcting a mistake is cheap and waiting is expensive. They're explicit that this would be irresponsible in a low-throughput setting. The right gate strictness depends on how cheap your corrections are, so measure that before copying the policy.

When the model changes

Harness components exist because of something a particular model does badly. When the model changes, some of those reasons disappear and new ones appear.

  • Remove what's no longer needed. Anthropic's March 2026 harness dropped context resets once Opus 4.5 no longer showed context anxiety, and dropped the per-sprint structure with Opus 4.6, while keeping the planner because the generator still under-scoped without it (Module 6).
  • Expect temporary guardrails. LangChain's advice is to design guardrails for today's shortcomings, such as blind retries and unverified work, and to expect some to become unnecessary as models improve.
  • Tune per model. Different models need different prompting and scaffolding. In LangChain's work, a Claude Opus 4.6 run scored 59.6% on an earlier harness version, below their tuned Codex run, because they hadn't run the improvement loop for Claude.

Co-evolution and overfitting

Coding models are now post-trained with their own harnesses in the loop, so they get better at whatever those harnesses emphasize: filesystem operations, bash, planning, subagents. That's mostly good. LangChain points out the downside, overfitting to a particular tool interface: a model can do worse when, say, the format of its file-editing tool changes, even though a capable model "should" adapt. Their conclusion is that the best harness for your task isn't necessarily the one the model was trained with. Test, don't assume.

Treat the harness as a product

A harness is software with users (the agents) and stakeholders (you). It deserves the same engineering discipline as the code it produces.

  • Version it and record the version on every run (Module 9).
  • Test it with the eval suite on every change (Module 10).
  • Flag it. Ship new middleware behind a flag and compare on a slice of traffic before switching it on everywhere.
  • Document why each part exists. A short record per component prevents the two classic mistakes: deleting something that was preventing a real failure, and keeping something nobody remembers the purpose of.

The removal test is the important line. It turns "should we still have this?" from a debate into an experiment you can run on every model upgrade.

Open problems

The field is young, and the primary sources are candid about what isn't solved yet.

  • Coherence. How do you keep hundreds of guides and sensors consistent as a harness grows, and how much should you trust an agent to resolve conflicting instructions? (Böckeler)
  • Harness coverage. There's no equivalent yet of code coverage or mutation testing for asking how much of the space of mistakes a harness can catch. (Böckeler)
  • Behavioral verification. Checking that software does the right thing, rather than that it's well-formed, still leans heavily on tests the agent wrote itself. (Böckeler)
  • Long-term architecture. How a fully agent-generated system's architecture holds up over years, and where human judgment adds the most leverage, is still unknown. (OpenAI)
  • Scale and self-improvement. Orchestrating hundreds of agents in parallel, having agents analyze their own traces to fix harness failures, and assembling tools and context just-in-time. (LangChain, Meta-Harness)
  • Generalization. Most published harness work is about coding. Whether the lessons carry to research, finance or operations is largely untested. (Anthropic)

Takeaways

  • Steer by changing the harness when a failure recurs; promote rules from docs into code when docs aren't enough.
  • Agents amplify existing patterns. Encode principles mechanically and run cleanup agents continuously.
  • Gate strictness should match how cheap corrections are in your setting.
  • Re-examine the harness with every model change; remove what no longer helps and tune for the model you run.
  • Version, test and flag the harness, and give every component a recorded reason and a removal test.

Check your understanding

A new model ships. What's the right first move for your harness?

Scaffolding costs tokens and latency. Measure each piece against the new model rather than assuming in either direction.

Why did OpenAI move from weekly manual cleanup to background agents?

Drift accumulates at agent speed, so the cleanup has to run at agent speed too, in small, quickly reviewable PRs.

According to LangChain, is the best harness for a model the one it was post-trained with?

Co-evolution helps on the primitives the harness emphasizes, but it can also make a model brittle to interface changes. Test alternatives on your own evals.

Exercise: write the records

For every middleware, hook and sensor you've built in this course, write a component record using the template above: the failure it addresses, the evidence, the signal that it works, and a removal test. Then run one removal test for real: disable a component on half your eval runs and see whether it's still earning its place.
