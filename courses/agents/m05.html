CrewAI: agents as a team with roles

CrewAI models a project the way a manager would: agents with roles, goals and backstories, tasks with expected outputs, and a crew that runs them in order or under a manager. Most of it is configuration in YAML. You'll run a debate, build a stock picker with a manager agent and memory, and assemble an engineering team that writes and tests code in a Docker sandbox.

By the end of this module you can

  • Scaffold a CrewAI project and define agents and tasks in YAML.
  • Run crews sequentially or hierarchically under a manager agent.
  • Give agents built-in and custom tools, structured outputs and memory.
  • Let agents run the code they write, safely, in a throwaway container.

Projects: a debate, a stock picker and an engineering team

  1. Create a debate crew: a debater argues for and against a motion, and a judge on a different model decides.
  2. Create a stock_picker crew: one agent finds companies in the news in a sector, another researches them, a third picks one and notifies you. Run it hierarchically with a manager, with Pydantic outputs and memory.
  3. Create a coder crew with sandbox tools that run Python in Docker, and ask it for a program whose output you can check.
  4. Grow it into an engineering_team: a lead writes a design, a backend engineer writes a module, a frontend engineer writes a Gradio UI for it, and a test engineer writes and runs unit tests.

Cost: cents per run with small models; the engineering team, with several long outputs, can reach a dollar with large ones. Needs Docker running for the last two projects.

Install and scaffold

CrewAI installs as a command-line tool, and each crew is its own small uv project. The scaffold gives you src/debate/config/agents.yaml, config/tasks.yaml, crew.py and main.py, plus a .env for that project's keys. Model names use the provider/model form, such as openai/gpt-5.4-mini or anthropic/claude-sonnet-4-5, which lets each agent run on a different provider.

Agents and tasks in YAML

Role, goal and backstory become the agent's system prompt; description and expected output become the task prompt. Placeholders such as {motion} are filled from the inputs you pass at kickoff. In a sequential crew, each task automatically sees the outputs of the tasks before it, which is how the judge reads both arguments.

The decorators collect methods into self.agents and self.tasks, in the order they're defined, and @CrewBase loads the two YAML files. Run crewai run again and read the three files in output/.

Tools, structured output and memory

The crewai-tools package has ready-made tools; SerperDevTool() searches Google through Serper with your SERPER_API_KEY. Custom tools are decorated functions, just like the Agents SDK:

output_pydantic makes a task return a validated object (read it from result.pydantic) and makes its output reliably parseable for the next task. memory=True turns on CrewAI's built-in memory, which stores what the crew learns in a local database using embeddings and recalls relevant items later, so a second run can avoid picking the same company. How memory is configured has changed between versions, so check the memory docs for yours.

Agents that run their own code

A coding agent is only useful if it can run what it writes, and you shouldn't let it run that code on your machine. The pattern: tools that read and write files in one sandbox folder, plus a tool that runs a file inside a fresh Docker container with only that folder mounted.

Three safety choices are doing the work: --rm throws the container away, --network none stops the code from reaching the internet, and the path check stops the agent writing outside the sandbox. Returning stderr as well as stdout lets the agent see and fix its own errors. CrewAI caches tool results by default, which is right for a search and wrong for a tool whose answer depends on files that just changed.

A good first brief is a small trading-account system: deposit, withdraw, buy and sell shares at prices from a given function, report holdings and profit, and refuse impossible trades. Opinionated, for better and worse

CrewAI gets a multi-agent team running quickly, and the YAML keeps prompts readable for non-programmers. The cost is control: the framework writes prompts around yours, and a hierarchical manager can loop or skip work. Use verbose=True and tracing to see the full prompts, prefer sequential crews until you need a manager, and keep each task's expected output specific.

Takeaways

  • Agents are role, goal, backstory and model; tasks are description, expected output and an agent. YAML holds both.
  • Sequential crews run tasks in order with earlier outputs as context; hierarchical crews add a manager that delegates.
  • output_pydantic for structured results, memory=True for recall across runs, custom @tool functions for anything else.
  • Agent-written code runs in a disposable, network-less container with one folder mounted.

Check your understanding

How does the judge in a sequential debate crew see the two arguments?

In a sequential process each task receives the outputs of the tasks before it.

Your run-code tool keeps returning the output of an earlier version of the file. Why?

Tool caching suits pure lookups. Disable it for tools whose results depend on changing state.

Which Docker option stops agent-written code from sending your data anywhere?

--rm deletes the container afterwards; only --network none removes network access.

Exercise: a crew for your own work

Design a three-agent sequential crew for a task you do regularly, such as preparing a weekly report or reviewing a document against a checklist. Give the last task an output_pydantic model with a pass/fail field. Then switch it to hierarchical with a manager and compare: did the manager improve the result, and how many more model calls did it take?
