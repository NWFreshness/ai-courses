Capstone: an autonomous trading floor

Everything comes together in one system that runs without you. Four trader agents, each with its own strategy and model, manage simulated portfolios. Each calls a researcher agent as a tool, and every capability, from accounts to market data to memory, arrives through an MCP server. A scheduler wakes them up, a custom trace processor logs what they do, and a dashboard shows the floor live.

By the end of this module you can

  • Design a multi-agent system where agents, tools and data are separated by MCP servers.
  • Wrap an agent with its own servers as a tool for another agent.
  • Run agents autonomously on a schedule, in parallel, with bounded turns and isolated failures.
  • Capture agent activity with a custom trace processor and show it in a live dashboard.

Project: four traders, one researcher, six servers

  1. Finish the accounts module from Module 7 so it records transactions, a strategy and a portfolio value over time, and serve it with tools and two resources (the account report and the strategy).
  2. Write a market-data server: a simulator that returns plausible prices, or a wrapper around a real market-data API if you have a key. Add a push-notification server.
  3. Build the researcher agent with fetch, search and memory servers, and turn it into a tool.
  4. Build a Trader class: four named traders with different strategies (and, optionally, different models), each running with its servers inside one trace.
  5. Add a scheduler that runs all four every N minutes with asyncio.gather, a trace processor that writes their activity to SQLite, and a Gradio dashboard that refreshes from it.

Cost: with a small model, each trader's run is a few cents; four traders every hour for a day comes to a few dollars. Start with long intervals and watch the usage page. All trading is simulated: no real money, and nothing here is investment advice.

The architecture

The researcher, as a tool

Each trader gets its own memory file, so Warren's notes about a company build up over many runs and don't leak into Cathie's. Filtering the search server down to plain search keeps the researcher from reaching for heavier, slower crawl tools.

The trader

read_resource is a small helper you write with the MCP client SDK: it starts the accounts server, opens a ClientSession and calls read_resource on the URI. AsyncExitStack opens a variable number of servers and guarantees they all close, even if the run fails. max_turns bounds each run. Alternating between trading and rebalancing gives the traders two different jobs to do, and the account's strategy text lives in the accounts server, where a trader can change it with a tool.

The floor, on a schedule

Give each trader a different starting strategy in its account, written in plain language: Warren buys undervalued companies and holds them, George makes bold bets on macro events, Ray follows systematic rules about risk parity, Cathie buys disruptive innovation. To compare models rather than strategies, give each trader a different model through OpenAIChatCompletionsModel, as in Module 3.

Seeing it: a trace processor and a dashboard

The SDK sends traces to OpenAI's viewer, and it also lets you add your own processor that receives every trace and span as it starts and ends. Write those events to a database, and your dashboard can show each trader's activity live.

Span types tell you what happened: agent, generation (a model call), function (a tool call, including MCP tools), mcp_tools (listing a server's tools) and handoff. For the dashboard, a gr.Blocks page with one column per trader is enough: a line plot of portfolio value over time, tables of holdings and recent transactions, and a log panel, all refreshed by a gr.Timer every few seconds from the database. Run the floor and the dashboard as two separate processes that share only the database files.

Autonomy changes what can go wrong

Nobody is watching a scheduled run. That's why the design bounds every run with max_turns, catches each trader's errors separately, keeps every capability behind a server you control, uses simulated money, and logs everything. Before giving an autonomous agent any real power, decide what it must never do, enforce that in the tools themselves (the accounts server refusing trades it can't afford, say), and add a human checkpoint for anything you couldn't undo.

Taking it further

  • A real front end. Put a small FastAPI app over the database (portfolio values, holdings, logs as JSON) and build a front end with Vite or any framework; the agents and servers don't change.
  • A real market. Swap the simulator for a market-data provider's MCP server or API. Some publish official servers; check which MCP SDK version they need.
  • Better research. Add a second researcher with a different search provider, or let traders share a common memory for market-wide facts while keeping their own for strategy.

Takeaways

  • Separating agents (decisions) from MCP servers (capabilities) keeps a multi-agent system testable and changeable.
  • Agents with their own servers become tools for other agents through as_tool.
  • Autonomous runs need bounded turns, isolated failures, constraints enforced in tools, and logs.
  • A custom trace processor turns the SDK's tracing into data your own dashboard can show.

Check your understanding

Why does each trader get its own memory file?

Separate memories keep each agent's knowledge, and its mistakes, its own. Shared memory is a deliberate design choice, not a default.

Where should the rule "never spend more cash than the account holds" live?

Instructions can be ignored or misread; a tool that refuses an impossible trade can't be argued with.

One trader's run raises an exception. What should happen to the other three?

By default an exception in one coroutine passed to gather propagates; catching inside each trader keeps failures isolated.

Exercise: a risk officer

Add a fifth agent that never trades: a risk officer who runs after the traders each cycle, reads every account through the accounts resources, and sends you a push notification if any portfolio has more than 40% in one stock or has lost more than 10% in a day. Give it read-only access by building its accounts server without the buy and sell tools. Then add an input to the dashboard that pauses any trader.
