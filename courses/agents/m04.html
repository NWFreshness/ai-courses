The OpenAI Agents SDK

Your first framework is also the lightest. The OpenAI Agents SDK gives you agents, a runner that does the loop, tools from plain functions, sessions, tracing and guardrails, and gets out of the way. It works with other providers' models too. You'll use it to build a sales team with a manager, and a research agent that plans, searches and writes.

By the end of this module you can

  • Create agents, run them with Runner, stream their output and read their traces.
  • Turn functions and whole agents into tools, and choose between tools and handoffs.
  • Get validated structured output, and plug in models from other providers.
  • Add input and output guardrails, and know exactly when they run.

Projects: a sales team, then a research agent

  1. Three writer agents, each with a different style, draft cold emails for a fictional product in parallel; a picker chooses the best.
  2. Rebuild it with a manager agent that calls the writers as tools and sends the winner with a real email tool.
  3. Add an emailer agent as a handoff, run writers on models from other providers, and add a guardrail that blocks requests naming a real person.
  4. Build a deep-research agent: a planner with structured output, parallel web searches, a writer that returns a report object, and an emailer, all orchestrated by code.
  5. Put the research agent behind a Gradio UI that streams its progress.

Cost: cents for the sales team. Each research run with a small model and five hosted web searches costs roughly ten to twenty cents; hosted search is billed per call on top of tokens.

Agents, runners and traces

Install it with uv add openai-agents and import from agents. (Don't run pip install agents: that's an unrelated, older package.) An Agent is configuration: a name, instructions, a model, and optionally tools. Runner.run executes the loop you wrote in Module 2 and returns a result whose final_output is the answer.

Every run is traced automatically to OpenAI's trace viewer at platform.openai.com/traces, and trace("…") groups several runs under one name. Open it after each example: you'll see every model call, tool call and handoff with its timing, which is the fastest way to understand what an agent actually did.

For streaming, Runner.run_streamed returns immediately; iterate over result.stream_events() and print text deltas as they arrive (events of type raw_response_event whose data is a ResponseTextDeltaEvent).

Tools from functions

@function_tool reads the function name, type hints and docstring (including an Args: section) and builds the JSON Schema from Module 2. That's the whole reason to use a framework at this level: the boilerplate you wrote by hand is now one line. Sync and async functions both work.

Memory with sessions

Each Runner.run starts fresh. To carry a conversation across calls, pass a session, which stores the history and replays it each time.

Orchestrating agents: by code, as tools, or by handoff

With several agents, someone has to decide who does what. The SDK supports three styles, and choosing well matters more than anything else in this module.

StyleHowWho's in controlUse it when
CodeSeparate Runner.run calls, asyncio.gatherYouThe steps are known. Most reliable and easiest to test
Agents as toolsagent.as_tool(...)The calling agent, which gets each result backA coordinator should choose which specialists to consult, and stay in charge
HandoffsAgent(handoffs=[other])Passes to the other agent, which continues the conversationTriage: route a user to the right specialist, which then owns the reply

A handoff is one-way: the receiving agent sees the conversation and takes over, and the first agent doesn't get control back. Give each handoff target a handoff_description so the model knows when to use it. Many practitioners find handoffs harder to reason about than tools, and start with code, moving to tools only where the model's judgment adds something.

Force a tool call

If an agent sometimes answers from memory instead of using its tool, set model_settings=ModelSettings(tool_choice="required"). The research agent's searcher below uses this so it always searches.

Other providers' models

Agents can run on any OpenAI-compatible endpoint. Wrap an AsyncOpenAI client in OpenAIChatCompletionsModel and pass that as the model. Tracing still uploads to OpenAI, so keep an OPENAI_API_KEY set, or turn tracing off with set_tracing_disabled(True).

Structured outputs

Set output_type to a Pydantic model and final_output becomes an instance of it, validated. Use Field(description=...): the descriptions go to the model and do as much as the instructions.

Guardrails

A guardrail is a check that runs alongside an agent and can stop the run by tripping a wire. Input guardrails inspect the request; output guardrails inspect the answer. The check can be plain code or another agent.

Where guardrails actually run

Input guardrails run only on the first agent in a run, on the initial input. Output guardrails run only on the last agent's final output. Put an input guardrail on an agent that's reached by handoff, or called as a tool, and it never fires. If you need a check at a particular step, the plain alternative is often clearer: a separate Runner.run of a checker agent, or a check inside the tool itself.

Project 2: a deep-research agent

Add an emailer agent with your send_email tool that turns report.markdown_report into a well-presented HTML email. Then make research an async generator that yields status lines ("Planning…", "Searching 5 terms…", "Writing…") followed by the report, and hand it to a gr.Blocks UI with a textbox, a button and a gr.Markdown output; Gradio streams whatever an async generator yields.

Why orchestrate this one by code

You could give one agent all these tools and say "research this". It works, until it decides two searches are enough, or forgets to email. Fixed steps in code, each with a typed output, make the pipeline predictable and every stage testable on its own. Save model-driven orchestration for the parts where judgment genuinely helps.

Takeaways

  • Agent is configuration; Runner.run is the loop; traces show what happened.
  • @function_tool turns a typed, documented function into a tool; as_tool does the same for an agent.
  • Orchestrate by code where you can, with agents as tools where judgment helps, and with handoffs for triage.
  • output_type gives validated objects; guardrails run only at the start and end of a run.

Check your understanding

You put an input guardrail on an agent that the triage agent hands off to. When does it run?

Input guardrails check the initial input to the first agent. Put the check on the triage agent, or inside the tools, instead.

A manager agent should consult three writers, compare their drafts and send one. Which fits best?

With a handoff the manager would lose control after the first writer. Tools return results to the caller, which stays in charge.

The searcher sometimes answers from memory instead of searching. What's the direct fix?

Requiring a tool call forces the model to use a tool on that turn.
