An agent loop from scratch

Every agent framework in this course wraps the same twenty lines of code. Write them yourself once and the frameworks stop being mysterious. You'll build a career assistant that answers as you, captures leads and pings your phone, check its replies with a second model, put it on the web, and then make the loop visible with a planning checklist.

By the end of this module you can

  • Describe tools to a model with JSON Schema and dispatch its tool calls safely.
  • Write an agent loop with a turn limit, handling several tool calls per turn.
  • Add an evaluator that checks replies against rules and triggers a retry.
  • Deploy a Gradio agent to a free host with its keys kept out of the code.

Project: a career assistant that works for you

  1. Export your LinkedIn profile (or CV) as a PDF and write a short summary.txt about yourself.
  2. Build a system prompt that has the model speak as you, grounded only in those two files.
  3. Give it two tools: record_user_details for visitors who leave an email, and record_unknown_question for anything it can't answer. Both push a notification to your phone.
  4. Wrap the loop in a Gradio chat interface, then add an evaluator model that rejects unprofessional or invented replies and asks for a rewrite.
  5. Deploy it to Render's free tier, then build the second project at the end of the module: a terminal agent that plans with a checklist.

Cost: cents to build; a hosted assistant answering a few visitors a day costs pennies with a small model.

The loop

Tools: a schema and a function

A tool is two things: a description the model reads, written in JSON Schema, and a function your code runs when the model asks. The model only ever sees the description, so write it the way you'd brief a new colleague: what the tool does, when to use it, and what each argument means.

Dispatch through an explicit dictionary of allowed functions. Looking names up in globals() works in a notebook, but it lets the model call any function in your program, which is exactly the kind of power you don't want to hand over by accident.

The loop itself

Three details carry the weight. The model can ask for several tools in one turn, so handle every call and return a result for each tool_call_id, or the next request fails. Append the model's own request before the results, so the history reads in order. And cap the turns: a model that keeps calling tools will otherwise keep spending.

Speaking as you

Run uv add pypdf, then uv run app.py. Ask it something your profile covers, then something it doesn't (your favorite food), then say you'd like to hire you and give an email. You should get two notifications. Stripping history down to role and content drops extra fields Gradio adds, which some providers reject.

Check before you send: an evaluator

A chatbot speaking in your name can embarrass you. Add the evaluator half of the evaluator-optimizer pattern: after each reply, a second model call checks it against your rules and returns a structured verdict. If it fails, rerun with the feedback in the system prompt.

parse with a Pydantic model asks the API for structured output and validates it, so verdict.acceptable is a real boolean, not text you have to interpret. Using a different model family as the judge catches more, because models share blind spots with themselves.

Put it on the web

Make the loop visible: planning with a checklist

The career assistant's loop is invisible: one or two tool calls, then an answer. Coding agents make their loops visible with a to-do list the model writes and ticks off. Two tools are enough to get the same behavior on any problem.

Write the two schemas, register both functions in a TOOLS dictionary, and run the same loop with a puzzle or a small analysis task and a higher max_turns. You'll watch a plan appear, then each step tick off in the terminal. Nothing about the loop changed; the tools gave the model a way to structure its own work.

This hands-on simulator needs JavaScript.

Tool errors that kill the loop

If a tool raises and you don't catch it, the whole run dies, usually mid-conversation. Catch exceptions inside the dispatcher and return the error as the tool result. Models are good at reading "No step 7. The checklist has 5 steps." and correcting themselves.

Takeaways

  • An agent is a loop: call the model, run what it asks for, append the results, repeat until it answers or a limit hits.
  • Tools are a schema the model reads plus a function you control; dispatch through an allow-list.
  • An evaluator with structured output turns "is this OK?" into a boolean you can act on.
  • Simple tools such as a checklist change how a model works, not just what it can reach.

Check your understanding

The model returns two tool calls in one response. You run only the first and call the model again. What happens?

Each tool_call_id in the assistant message needs a tool message answering it before the conversation can continue.

Why is dispatching through globals() risky outside a notebook?

An explicit allow-list means only the functions you chose to expose can ever run.

What does the evaluator add that a stricter system prompt can't?

Prompts shape behavior; an evaluator verifies the result. Together they catch more than either alone.
