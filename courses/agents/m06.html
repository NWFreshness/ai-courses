LangGraph and LangChain: agents as state machines

LangGraph treats an agent as a graph: nodes that do work, edges that decide what runs next, and a typed state that flows through it, saved after every step. That buys you things the lighter frameworks don't: pause and resume, replay from any earlier step, and human approval in the middle of a run. LangChain's agent layer and Deep Agents sit on top. You'll use all of it to build a personal co-worker that checks its own work.

By the end of this module you can

  • Place LangChain, LangGraph, create_agent and Deep Agents in one picture, and pick the right layer.
  • Build a graph with state, reducers, tool nodes and conditional edges.
  • Persist runs with checkpointers, inspect history, and resume after a human decision.
  • Use middleware, MCP tools and sub-agents, and add an evaluator node with success criteria.

Project: Sidekick, a co-worker that checks its own work

  1. Build a chatbot graph with a search tool and a push-notification tool, using ToolNode and tools_condition, and give it memory with a checkpointer.
  2. Rebuild the same agent in a few lines with create_agent, then add middleware that logs tool calls and asks your approval before any notification is sent.
  3. Give it a real browser through the Playwright MCP server, and a sandboxed folder for files.
  4. Build Sidekick: a worker node plus an evaluator node that checks each answer against success criteria you type, sending it back with feedback until it passes or needs you.
  5. Wrap it in a Gradio UI with a box for the request and one for the success criteria.

Cost: cents per task with a small model; browsing tasks use more tokens because pages are long. LangSmith tracing has a free tier.

Graphs: state, nodes, edges

The state is a typed dictionary that flows through the graph. Each node is a function that receives the state and returns an update. By default an update replaces a field; a reducer says how to combine instead. add_messages appends new messages to the list, which is what a conversation needs.

ToolNode runs whatever tools the last message asked for; tools_condition is a ready-made router that goes to the node named "tools" when there are tool calls and ends otherwise. The edge back from tools to chatbot is the loop. graph.get_graph().draw_mermaid() draws it for you.

Checkpoints: memory, history, time travel

A checkpointer saves the full state after every step, keyed by thread_id. That one feature gives you conversation memory (the second call above remembers the first), durability, and history. MemorySaver keeps checkpoints in memory; for something that survives restarts, swap in SQLite:

Each snapshot has its own checkpoint ID. Invoke the graph with a config containing an earlier checkpoint_id and it resumes from that point, which is how you replay or branch a run to debug it ("time travel").

The agent layer: create_agent and middleware

Most of the graph above is the same in every tool-using agent, so LangChain packages it. create_agent builds the loop on LangGraph; middleware lets you run your own code before or after model calls, or around each tool call.

The run pauses before the gated tool, saves itself in the checkpointer, and returns an interrupt describing what it wants to do. Your code (or a UI) shows that to a person, and Command(resume=...) continues the same run from exactly where it stopped. Pass a Pydantic model as response_format to get a typed answer in result["structured_response"].

LangChain ships ready-made middleware for common needs: SummarizationMiddleware to keep long conversations inside the context window, PIIMiddleware to redact emails or card numbers, ModelCallLimitMiddleware to cap a run, TodoListMiddleware to give the agent a plan it keeps updated, and retry middleware for flaky calls.

Tools from MCP servers

The langchain-mcp-adapters package turns any MCP server's tools into LangChain tools. Module 7 explains MCP properly; for now, it's how Sidekick gets a real browser.

Deep Agents

Long tasks need more than a loop: a plan, somewhere to put intermediate work, and a way to hand pieces to helpers without flooding the main context. create_deep_agent preassembles those: a to-do tool, file tools on a backend you choose, and sub-agents it can delegate to.

Each sub-agent works in its own context and returns only its result, so the lead's context stays small. Deep agents can also load skills: folders with a SKILL.md of instructions (and any helper files) that the agent reads only when a task calls for them.

Async tools in a sync graph

MCP tools from MultiServerMCPClient are async-only. If any node uses them, run the graph with await graph.ainvoke(...), and make your nodes async def with await llm.ainvoke(...). Mixing sync invoke with async tools raises an error about calling an async tool synchronously.

Takeaways

  • LangGraph models an agent as typed state, nodes and edges; reducers such as add_messages say how updates combine.
  • Checkpointers save every step by thread: memory, durability, history and time travel come from that one feature.
  • create_agent is the standard loop; middleware adds logging, limits, redaction and human approval with resumable interrupts.
  • Deep Agents add planning, files and sub-agents; an evaluator node turns success criteria into a loop that checks itself.

Check your understanding

Without the add_messages reducer on messages, what would each node's update do?

Without a reducer, a returned value replaces the field. add_messages appends (and updates by ID).

Why does HumanInTheLoopMiddleware need a checkpointer?

An interrupt ends the current call. Resuming with Command(resume=...) reloads the saved state for that thread.

In Sidekick, when does the graph end without the criteria being met?

The router ends on success or when the worker needs the user. In practice you'd also add a cap on loops, for example with ModelCallLimitMiddleware or a counter in the state.
