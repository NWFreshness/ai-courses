Production and safety

Every project in this course runs on your machine, with you nearby and small sums at stake. Production agents run unattended, for other people, with real permissions. This module lists what changes, shows how to evaluate an agent rather than eyeball it, and gives you a safety checklist to apply before an agent gets any power you'd regret.

By the end of this module you can

  • Name the gaps between a course project and a production agent.
  • Build an evaluation suite that checks outcomes and the path taken, and run it on every change.
  • Apply least privilege, sandboxing, approvals and limits to an agent's tools.
  • Decide what to learn next, and where the Harness Engineering course picks up.

Project: harden one agent you built

  1. Pick one project from the course: the career assistant, the research agent, Sidekick or the trading floor.
  2. Write 15–30 evaluation tasks for it with checks that a script can score, and record a baseline.
  3. Walk the safety checklist below and fix the top three gaps.
  4. Add a cost budget and alerts, then re-run the evaluation and compare.

Cost: an evaluation run costs the same as running the agent that many times; use a small model for judging where you can.

Evaluating agents

An agent's output varies run to run, and so does the path it takes. Evaluate both. A task suite is a list of realistic inputs, each with checks your code can run:

Prefer checks code can score: a tool was or wasn't called, a file exists, a test passes, a number is in range. Use a model judge with a written rubric only for qualities code can't check, and review a sample of its rulings yourself. Run each case several times and track the pass rate, because one pass proves little about a system that varies. Keep the suite in version control and run it whenever you change a prompt, a tool, a model or a framework version.

Every failure becomes a test

When an agent does something wrong in use, add that input to the suite before you fix it. Over time the suite becomes a record of everything that has ever gone wrong, and a guarantee that it won't go wrong the same way twice.

A safety checklist for agents with tools

  • Least privilege. Each tool does one narrow thing. Each agent gets only the tools its job needs. Keys have the smallest scopes the service offers.
  • Constraints in tools, not prompts. Limits that matter (spend, recipients, paths, row counts) are enforced in the tool's code, which refuses and explains.
  • Sandboxing. Agent-written code runs in a throwaway container or VM with no network unless needed and only the files it needs.
  • Separate untrusted input from powerful actions. An agent that reads web pages, emails or user uploads shouldn't also hold tools that send, pay or delete, unless a human approves each use.
  • Approval for the irreversible. Sending, paying, deleting and publishing pause for a person (Module 5's interrupts), with the exact action shown.
  • Limits on everything. Turns per run, runs per hour, spend per day, retries per task.
  • Logs you can audit. Every tool call with its arguments, result, the run it belonged to and who started it.
  • A stop button. A way to pause one agent or all of them without a deploy.

Takeaways

  • Production adds evaluation, budgets, durability, scoped identities, injection defenses and human oversight.
  • Evaluate outcomes and paths with code-scored checks, several runs per case, on every change.
  • Enforce limits in tools; keep untrusted input away from powerful, irreversible actions.
  • Every failure in use becomes a new test case.

Check your understanding

An evaluation case passes once. Why run it several times?

Track pass rates per case. A case that passes two times in three is a problem a single run would hide.

An email-triage agent reads incoming mail and can forward messages. What's the safest change?

Emails are untrusted input. A constraint enforced in the tool holds even if the model is misled; a prompt instruction might not.

Which check should you prefer in an evaluation suite where possible?

Code-scored checks are cheap, fast and consistent. Save model judges for qualities that need them, and spot-check them.

Exercise: a red-team afternoon

Take the agent you hardened and try to make it misbehave: hide instructions in a web page it will read, ask it to exceed its limits politely and then insistently, and feed a tool an input that makes it fail halfway. Add every successful attack to the evaluation suite as a case that must fail safely, then fix the agent until the suite passes.
