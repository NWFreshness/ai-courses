Five more frameworks, one worker

There are dozens of agent frameworks, and they rhyme. The fastest way to learn a new one is to build the same small thing in it: an agent, a run, some tools, an MCP server, and a loop toward a goal. This module does that five times on one shared task board, connects agents across frameworks with the A2A protocol, and ends with a team of those workers coordinated by an orchestrator agent.

By the end of this module you can

  • Build the same tool-using, MCP-connected worker in Google ADK, Pydantic AI, Strands, Microsoft Agent Framework and Agno.
  • Map any new framework onto five questions: agent, run, tools, MCP, loop.
  • Expose an agent over A2A and call it from another agent.
  • Coordinate several workers through shared state, and choose a framework for a job.

Project: one worker, five ways, then a team

  1. Write board.py, a tiny SQLite task board of goals and steps that any framework can use.
  2. In each framework, build a worker that reads the board, plans steps under its goal, does the work with files from a filesystem MCP server scoped to one folder, and ticks each step off. The test task: translate notes.txt into Spanish and write spanish.txt.
  3. Expose the ADK worker as an A2A service and call it from a second agent.
  4. Make each worker accept a task ID on the command line, then write an orchestrator agent that launches workers on different tasks, waits for them, checks their output, and sends one back to fix a problem.

Cost: cents per worker run. ADK examples default to a Gemini model, which needs a free GOOGLE_API_KEY; every framework here can use OpenAI instead.

The shared board

The worker's tools are ordinary typed, documented functions, and the file tools come from the official filesystem MCP server, started with npx -y @modelcontextprotocol/server-filesystem <folder>, which refuses any path outside the folder you give it. The only thing that changes between frameworks is the glue.

The same worker, five times

ADK takes plain functions as tools directly. Put the agent in a package whose agent.py defines root_agent, and adk web opens a local developer UI where you can chat with it and inspect every event, while adk run does the same in the terminal.

A bare Agent() in Strands defaults to a model on Amazon Bedrock, which needs AWS credentials; passing an OpenAIModel avoids that. Strands also offers a @tool decorator when you want to control a tool's name or description.

Microsoft Agent Framework is the successor to AutoGen and Semantic Kernel, for teams in the Microsoft and Azure world. Agno pairs its agent library with a runtime for serving agents. If you work in TypeScript, Mastra is the equivalent there: new Agent({ name, instructions, model: "openai/gpt-5.4-mini", tools }), tools built with createTool and zod schemas, and MCP through @mastra/mcp's MCPClient.

Look at how little differs. Every framework takes typed, documented functions as tools, connects to the same MCP server over stdio, and runs the same loop. The real differences are elsewhere: default models and clouds, how runs are served and observed, multi-agent features, and how stable the APIs are.

Agents talking across frameworks: A2A

MCP connects an agent to tools. The Agent2Agent (A2A) protocol connects an agent to another agent, possibly in another framework or organization. An A2A agent publishes an agent card (its name, skills and endpoint, at a well-known URL) and accepts tasks over HTTP. ADK can serve an agent this way and call remote ones as if they were local sub-agents.

From workers to a team

Give each worker an optional task ID and board path on the command line: run bare, it seeds its own demo goal; given a task, it claims that one, works it, marks it done and exits. The orchestrator is itself an agent (in ADK, say) with a handful of tools you write:

  • launch_worker(framework, objective) adds a task to the board and starts that framework's worker as a subprocess, returning at once.
  • wait_for_team() blocks until every launched worker exits or times out, then returns the board.
  • test_output(task_id) hands the result to a short-lived QA agent with a browser (the Playwright MCP server) that tries it and reports a verdict.
  • relaunch_worker(framework, problem) adds a fix task describing the symptom and runs that worker once more. Allow one fix per task, so a broken result is reported rather than retried forever.

A good brief for the team is a small arcade of browser games that teach a language, one game per framework, each a single HTML file in a shared folder. The board shows progress live, the QA agent catches games that don't load, and the outer loop (launch, wait, test, fix) is the same shape as the inner one each worker runs.

Two workers, one task

When several workers share a board, two can grab the same task. The claim function above avoids that with a single conditional UPDATE: only one worker's update matches status='pending', and the other gets False and moves on. Never read a status and then write it in two separate steps.

Takeaways

  • Every framework answers the same five questions: how to make an agent, run it, add tools, add MCP, and loop toward a goal.
  • Keeping tools as plain functions and MCP servers makes them portable across all of them.
  • A2A connects agents to agents through published cards; MCP connects agents to tools.
  • Teams coordinate best through shared state with atomic claims, and an orchestrator that tests results before accepting them.

Check your understanding

You create Agent(system_prompt=...) in Strands with no model, and it fails with an AWS credentials error. Why?

Pass an explicit model, such as OpenAIModel(...), to use another provider.

What's the difference between MCP and A2A?

An A2A agent publishes a card describing its skills and accepts tasks; an MCP server exposes tools, resources and prompts.

Why does the orchestrator limit each task to one fix attempt?

Bounded retries are a basic guard on autonomous loops: cost and time stay predictable, and humans see what failed.

Exercise: a sixth framework

Pick a framework not covered here and build the worker in it, using only its documentation and the five questions. Time yourself. Then add a --model option to every worker and run the same task on two models: does the framework or the model matter more for whether the task gets done?
