Frontier models and structured decisions

Wayfarer's brief arrives today. Before building anything elaborate, find out what one model call can do: give it a claim, the customer's policy and the wording, and get back a decision your code can use. Then try the same job as an agent, and see that more autonomy isn't automatically better.

By the end of this module you can

  • Explain how a model becomes a product: tokens, context, reasoning, memory and tools.
  • Compare models on intelligence, speed and cost, and shortlist them for a task.
  • Get validated structured decisions from a model, with the reasoning written first.
  • Decide whether a task needs an agent or a single call, from measurements.

Build: decide the first 25 claims

  1. Write 25 sample claims for Wayfarer (or generate them), each with a customer, a policy and a handler's decision you agree with: the answer key.
  2. Decide each claim with one structured call: the claim, the policy record and the wording go in, a ClaimDecision comes out.
  3. Score against the answer key and compare two or three models on accuracy, cost and time.
  4. Do the same job with an agent that has two tools, get_policy and record_decision, and compare.

Cost: a few cents for 25 claims on a small model; free on openrouter/free, with noisier results.

From a model to a product

A language model only predicts the next token. Six ideas turn that into something like a chat assistant, and you'll use each of them deliberately:

IdeaWhat it means in practice
AutoregressionText is produced one token at a time, each conditioned on everything before it, so what the model writes first shapes what follows
ChatTraining on conversations turns completion into question and answer, with system, user and assistant roles
ReasoningReasoning models write hidden working before answering; effort settings trade cost and time for accuracy
The illusion of memoryEvery call is independent. The "memory" is your code sending the whole conversation again
ContextEverything the model knows about this task is what's in the window: the policy wording, the claim, the history
ToolsThe model can ask your code to do something and read the result, which is how agents act

You pay per token: input, cached input (cheaper, when the start of a prompt repeats exactly), reasoning and output (most expensive). Put the long, unchanging part of a prompt, such as the policy wording, first and the claim last, so repeated calls can hit the cache.

Choosing models

Public leaderboards such as Artificial Analysis plot models on intelligence, speed and price. The useful ones lie on the Pareto front: no other model is both better and cheaper. Measures such as METR's task time horizons show how long a task an agent can complete reliably. Use benchmarks to shortlist; then test the shortlist on the client's actual task, because that's the only result that counts.

The brief and the target

Wayfarer's head of claims wants claims "handled straight through, as accurately as our handlers". Turn that into numbers you can measure before you build: accuracy (right decision and a payout within a dollar of the handler's), the straight-through rate (claims not referred), and a rule that every payout over $1,000 waits for a handler's sign-off. Without agreed numbers, there's no way to say when the pilot works.

A decision as data

The order of the fields matters. Because the model writes fields in order, putting rationale first makes it explain itself before committing to a decision and a number, which tends to improve both. The Literal type means the answer can only be one of three strings your code understands.

The same job as an agent

Now let an agent do it: give it get_policy(policy_id) and record_decision(claim_id, decision, payout, rationale) and only the claim. It has to look up what the single call was handed directly. Run both on the same claims and compare.

This hands-on simulator needs JavaScript.

The usual result: the agent takes longer, costs more and does no better. Deciding a claim from known inputs is a fixed workflow, and code that gathers the inputs is more reliable than a model deciding to. Agents earn their place when the path can't be known in advance; the reference course reaches the same conclusion on its own claims.

Claims your inputs can't decide

Some claims depend on rules that live outside the policy wording, such as how to treat a third claim in a year, which sits in the claims manual. If those rules aren't in the context, expect the model to get those claims wrong whichever approach you use. Check what a claim needs before blaming the model.

Takeaways

  • Models are products built from tokens, context, reasoning, replayed memory and tools; you pay for every token.
  • Shortlist models with benchmarks, then decide on the client's task.
  • Agree measurable success criteria before building.
  • Structured output turns a decision into data; put the rationale first.
  • A fixed workflow is usually better done as code plus one call than as an agent.
