Building with coding agents

An FDE has days, not months. Coding agents make it possible to build a working pilot in an afternoon, but only if you stay in charge: clear documents for the agent to work from, a plan you check, and automatic gates that stop broken code from landing. Today a coding agent builds Wayfarer's pilot, and you're the boss.

By the end of this module you can

  • Choose a coding agent and set it up with an instructions file and MCP tools.
  • Write the documents that let an agent build what the client asked for.
  • Run a plan-then-implement workflow with verifiable success criteria per phase.
  • Put automatic quality gates in front of every commit, and know what humans must still own.

Build: the pilot

  1. Write docs/SPEC.md (the client's brief in their words), docs/TECH_STACK.md, docs/PROCESS.md and a short AGENTS.md that points to them.
  2. Set up the gates: linting, type checks, unit tests with a coverage floor, end-to-end tests and a pre-commit hook, all run by one command.
  3. Add the Playwright MCP server so the coding agent can check pages in a browser.
  4. Ask the agent to plan the pilot into phases; review and edit the plan; then ask it to implement the plan, phase by phase, committing after each.
  5. Review what it built yourself, run the queue, and write down what you'd change.

Cost: a subscription to a coding agent, or a free one such as OpenCode with free models (expect to work in smaller steps).

Be the boss

  • You own what ships. "The agent wrote it" is not an answer a client accepts.
  • Instructions as a map. Keep AGENTS.md short and point to detail (progressive disclosure), so the agent reads the spec when it needs the spec.
  • A fresh context per task. Start a new session for each piece of work rather than one endless conversation.
  • Plan, check, then build. Ask for a plan in phases, each with success criteria the agent can verify itself: tests, commands and their output, pages checked in a browser. Read it before saying go.
  • Commit often, so any phase can be undone.

Gates, not hope

Agents write plausible code quickly, including plausible bugs. Automatic checks are what make speed safe: linting and formatting (ruff, ESLint, Prettier), static types (pyright, strict TypeScript), unit tests with a coverage floor (pytest, vitest), end-to-end tests in a real browser (Playwright), all behind one command such as npm run check, and a pre-commit hook (lefthook or pre-commit) that runs the fast ones on every commit. The rule that matters most: the agent may never weaken a check to make it pass. If a rule looks wrong, it stops and asks.

Let the agent see the app

With the Playwright MCP server, a coding agent can open the dashboard, click through it and check what it built, instead of guessing. In Claude Code: claude mcp add playwright -- npx @playwright/mcp@latest. Added this way it's local to you in this project; --scope user makes it available in all your projects, and --scope project shares it with your team through a checked-in file.

The shape of the pilot

Whatever the agent builds, insist on a few design rules in the spec, because later weeks depend on them:

  • A backend API (FastAPI with SQLite is plenty) owns the records. The agent reaches claims, policies and its own instructions only through that API.
  • Every operation has a clear name and a one-line description, which later become the agent's tools.
  • Paying a claim is its own operation that takes the amount, and the backend, not the agent, enforces the $1,000 sign-off rule.
  • A dashboard shows the queue, each claim with the agent's reasons, and the agent's steps as it works.

Passing tests aren't a review

A build can pass every check and still be messy: duplicated logic, prompts that spell out every step instead of stating the goal, names nobody would choose. Read the code. Many teams now add a review by a fresh agent, with no memory of writing the code, before each commit, and keep a human review of anything that matters.

Takeaways

  • Coding agents are harnesses around models; you are accountable for their output.
  • Short instructions that point to detailed docs, a fresh context per task, a reviewed plan with verifiable criteria, frequent commits.
  • Automatic gates catch what agents get wrong; never let an agent weaken them.
  • Put business rules such as payment limits in the system, where a model can't talk past them.

Exercise: review like a lead

Review the pilot your coding agent built as if a junior engineer had sent it: list five concrete problems (naming, duplication, missing tests for a business rule, a prompt that dictates steps, anything else), ask the agent to fix them one at a time in fresh sessions, and commit after each. Write a short PILOT.md with what you'd tell the client today.
