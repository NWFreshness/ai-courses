Open-weight models and token cost

Sooner or later a client asks whether they can run the model themselves: for privacy, for control, or because they think it'll be cheaper. An FDE needs a crisp answer. This module covers what open weights do and don't buy you, how to read a model's name, what fits on which hardware and how fast it'll run, and how to work out the cost of every decision.

By the end of this module you can

  • Explain proprietary, open-weight and open-source models, and when open weights are worth it.
  • Read a model's name: size, active parameters, quantization and file format.
  • Estimate whether a model fits on a machine and how fast it will generate.
  • Compare models on accuracy, cost per claim and time, and choose from the Pareto front.

Proprietary, open-weight, open-source

KindWhat you getExamples of the kind
ProprietaryAn API. The weights stay with the labOpenAI's, Anthropic's and Google's frontier models
Open-weightThe trained weights to run where you like, under a licenseLlama, Qwen, Gemma, DeepSeek, gpt-oss
Open-sourceWeights plus training code and data, so the model can be reproducedA smaller group, such as AllenAI's OLMo

Open weights are mostly about privacy and control: the data never leaves your infrastructure, nobody can retire the model under you, and you can fine-tune it. They aren't automatically cheaper. A GPU you rent sits idle between requests, while an API charges only per token, so at low or bursty volume an API usually wins on cost.

Reading a model's name

Take Qwen3-30B-A3B-Instruct-Q4_K_M.gguf: a Qwen 3 model with 30 billion parameters in total, of which about 3 billion are active for each token (a mixture of experts), tuned to follow instructions, quantized to roughly 4 bits per weight with the K_M scheme, in the GGUF file format.

  • Dense or mixture of experts. A dense model uses every weight for every token. A mixture of experts routes each token through a few expert blocks, so it has the knowledge of a large model and the speed of a small one, but it still needs memory for all its weights.
  • Quantization. Storing weights in fewer bits. 8-bit costs little quality; 4-bit starts to show on hard tasks. Quantization-aware training (QAT) trains the model to expect it, which narrows the gap.
  • Formats. safetensors for full-precision weights (Hugging Face, vLLM), GGUF for quantized models on llama.cpp, Ollama and LM Studio, MLX for Apple silicon.

What fits, and how fast

Memory needed is roughly the parameters times the bytes per weight, plus room for the context. Speed is set mostly by memory bandwidth: to produce each token the hardware reads every active weight once, so tokens per second is at most bandwidth divided by the active weights' size.

Running and hosting

For a laptop, Ollama and LM Studio are the easy route; llama.cpp gives you control; vLLM is the server for serious throughput on GPUs. Beyond your own machine, you can rent a GPU (Runpod and others), use a managed endpoint, or call open models through OpenRouter. The cost of a decision

A baseline before a leaderboard

Before comparing models, score the dumbest strategy: approve every claim. On a queue where most claims deserve approval, that alone can get most decisions right. A model that barely beats it isn't doing much, which is why Module 5 adds stricter scores.

Takeaways

  • Open weights buy privacy and control; they aren't automatically cheaper.
  • A model's name tells you its size, active parameters, quantization and format.
  • Memory sets what fits; bandwidth divided by active weights sets the speed.
  • Pin providers for consistent results, work out cost per decision, and choose from the Pareto front under the client's constraints.

Check your understanding

Why does a 30B mixture-of-experts model with 3B active parameters run much faster than a dense 27B model on the same laptop?

Generation speed is bandwidth-bound by the weights read per token. It still needs memory for all 30B.

A client wants open weights "to save money" on 200 claims a day. What's the honest answer?

Dedicated hardware costs the same whether or not it's busy; per-token APIs scale with use.

Why pin providers when calling an open model through OpenRouter?

The same model name can behave differently at different precisions and serving stacks.
