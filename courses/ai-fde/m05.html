Harness engineering

The pilot's agent works, but it's naive: one long conversation for the whole queue, no access to the claims manual, nothing to say what happens when a claim fails. Agent = model + harness, and the harness is where an FDE's judgment shows. Today you compare two ready-made harnesses, then give Wayfarer's agent a proper one of its own.

By the end of this module you can

  • Name the parts of a harness and decide what to build and what to buy.
  • Run the same job on the Claude Agent SDK and on Deep Agents, and compare them.
  • Give an agent a fresh context per unit of work, with a one-line report back.
  • Give it searchable documents, and clear rules for failures and hand-offs to people.

Build: Wayfarer's harness

  1. Make a "claims desk" folder of five claims and the wording, and have both ready-made harnesses work it with a claim-handler subagent that writes a decision file per claim and a handover note at the end.
  2. In the product, split the agent in two: a queue agent that keeps a to-do list (shown on the dashboard) and a work_claim helper that decides each claim in a fresh context and reports back in one line.
  3. Give the claim agent tools to search the policy wording and the claims manual and read one section at a time.
  4. Add failure rules: a claim that fails goes back in the queue once, and a second failure leaves it for a handler.

Cost: about 40 cents for the Claude Agent SDK run on a mid-size Claude model; a few cents for Deep Agents on a cheap open model.

From prompts to harnesses

The craft has moved from prompt engineering (the right words) to context engineering (the right information at the right time) to harness engineering: all the software around the model that makes it dependable. Its parts:

PartQuestion it answersIn Wayfarer
ContextWhat does the model see, and when?Searchable wording and manual, one claim per context
WorkflowWhich steps are fixed, which are the model's choice?Code drives the queue; the model decides each claim
StateWhat survives between steps and restarts?Claim status in the database, the to-do list
SubagentsWhat work gets its own context?One claim agent per claim
PermissionsWhat may it do without asking?Pay up to $1,000; larger payouts wait for sign-off
ObservabilityWhat did it do, and why?Steps on the dashboard; traces from Module 5
Self-improvementHow does it get better?The improver in Module 9

You use a harness every day, your coding agent. With Wayfarer you build one. Build or buy is a spectrum: direct API calls; LangChain's create_agent, a loop with middleware; Deep Agents, which adds planning, files and subagents; and the Claude Agent SDK, which gives you the harness behind Claude Code. The choice of framework matters less than what you do with it.

Two ready-made harnesses, one job

Note what you didn't write: no tools for reading files or tracking work, no subagent plumbing. Both harnesses bring those. Note also the guardrails you did set: a working folder, the tools allowed, no permission prompts in an unattended run, and a spending cap.

Wayfarer's own harness

For the product you want more control than a general-purpose harness gives, so build it on create_agent. The key move is a fresh context per claim: the queue agent never sees a claim's details, only a one-line result, so its context stays small however long the queue, and one strange claim can't confuse the next.

Documents the agent can search

The claims manual is long, and most claims need one or two sections of it. Rather than pasting it into every prompt, give the claim agent two tools: search_documents(query) returns matching section titles with a line of context, and read_section(document, section) returns one section. This is progressive disclosure for an agent: it pays for the text it needs, when it needs it.

Three outcomes that look alike

StatusMeansWho acts next
ReferredThe agent decided the claim needs a person's judgment or more informationA handler, as a decision
Waiting for sign-offThe agent approved a payout over $1,000A handler signs off, then it's paid
Left for a handlerThe agent failed twice to finish the claimA handler works it from scratch

Keep them apart in the data and on the dashboard. Mixing them up makes the straight-through rate meaningless and hides failures as if they were judgments.

Goals, not scripts

Generated prompts tend to list every step: "first call get_claim, then call get_policy, then…". That makes the agent brittle and hides what matters. Write the goal (decide the claim as a careful handler would, against the wording and the manual), the rules that must hold, and what a good result looks like, and let the model choose its steps.

Takeaways

  • Agent = model + harness: context, workflow, state, subagents, permissions, observability, self-improvement.
  • Ready-made harnesses give you files, planning and subagents; your own gives you control.
  • A fresh context per unit of work keeps the coordinator small and isolates failures.
  • Search-and-read tools beat pasting long documents; distinguish referrals, sign-offs and failures.

Check your understanding

Why does work_claim return one line instead of the claim agent's full conversation?

The subagent pattern is a context firewall: detail stays where it's used.

The agent approves a $1,400 payout. Which status should the claim show?

It's a decision (approve) held for a handler's sign-off, not a referral and not a failure.

What's the advantage of search_documents and read_section over putting the whole manual in the prompt?

Just-in-time retrieval saves tokens and keeps the relevant text prominent.
