Production deployment

The app and the context server are in the cloud; the agent still runs on your laptop. Today it moves to a managed agent runtime, where each request gets an isolated session, secrets come from an identity service, and you pay only while a session works. You'll also bring back the sign-off pause, now with a second option for the handler: send it back with a note.

By the end of this module you can

  • Configure an agent for production: settings, secrets, callers, limits, logs and cost.
  • Develop, deploy, invoke and remove an agent with the AgentCore CLI.
  • Design work across sessions: long dispatches, cold starts, and claims resumed in a new session.
  • Prevent two dispatches running at once with a lock and a heartbeat.

Build: the agent on a managed runtime

  1. Deploy a hello-world agent with the AgentCore CLI, then a small LangGraph agent; compare a cold and a warm session.
  2. Pause a claim in one session and resume it in another with a handler's note, from checkpoints in Postgres.
  3. Turn the agent's service into an AgentCore app that runs the same on your laptop and on Runtime, with its secrets in AgentCore Identity.
  4. Bring back the approval pause with two buttons: Sign off (the app pays) and Send back with a note (the agent decides again).
  5. Add a run lock in the database with a heartbeat from the agent, then run a swarm from the deployed dashboard.

Cost: Runtime charges only while a session is working, so cents. The CLI's first deploy creates a bootstrap stack with a KMS key at about $1 a month; delete it when you finish. The free route runs the agent as a second Render service.

Configuring an agent for production

ConcernOn Wayfarer
SettingsModel, gateway URL, memory ID as environment variables; nothing hard-coded
SecretsThe OpenRouter key and database URL in AgentCore Identity, fetched at run time
Who may call itOnly the app's role, through IAM
LimitsSessions stop after a short idle timeout (60 seconds), but a session doing registered background work can run for hours
Logs and costRuntime logs to CloudWatch; per-claim cost is recorded by the app; budget alerts stay on

The AgentCore CLI

The same file runs under agentcore dev and on Runtime, so what you test locally is what you deploy. Credentials come from a local env file in development and from AgentCore Identity once deployed.

Sessions and long work

  • One session, one dispatch. Starting a dispatch answers immediately ("started") while the dispatcher and its claim agents keep working in that session.
  • Cold and warm. A new session takes seconds to start; a warm one answers fast. Don't create a session per tiny request if latency matters.
  • Resuming elsewhere. A claim sent back days later resumes in a brand-new session, because its state is in Postgres checkpoints, not in the session's memory.
  • One run at a time. The app takes a lock in the database before starting a dispatch, and the agent refreshes a heartbeat while it works. A second start is refused while the heartbeat is fresh; a stale heartbeat (the agent died) releases the lock.

Sign off, or send back

A claim over the limit pauses again, now with two choices. Sign off: the app pays immediately (the handler is the authority), then a short session lets the agent finish the claim's graph and save it to memory. Send back with a note, for example "the taxi receipt is in twice": the agent resumes in a new session with the note and decides again, which may pause again for sign-off.

Port clashes and stuck locks

agentcore dev and the locally run agent both use port 8080, so stop one before starting the other. If the app restarts in the middle of a dispatch, new starts are refused until the heartbeat goes stale; reset it deliberately, never by deleting the lock while work may still be running.

Takeaways

  • Production means settings in config, secrets in an identity service, restricted callers, limits, logs and budgets.
  • One entrypoint runs locally and on the managed runtime; the CLI covers create, dev, deploy, invoke and remove.
  • Long work lives in a session; state that must outlive it lives in checkpoints.
  • A database lock with a heartbeat keeps one dispatch at a time without getting stuck forever.
