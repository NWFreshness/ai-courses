Agent swarms

One agent working claims one at a time is fine for a pilot. On a Monday morning with 400 claims in the queue, Wayfarer needs many at once. Today you replace the queue agent with a dispatcher that fans claims out to parallel claim agents, and meet the limits that decide how fast a swarm can really go: rate limits, connection pools and retries that must never repeat a payment.

By the end of this module you can

  • Tell teams, swarms and fleets apart, and know when parallel agents help.
  • Build a dispatcher in LangGraph that fans out work with Send and caps concurrency.
  • Handle rate limits with retry policies, and size concurrency to the slowest shared resource.
  • Measure time, cost and accuracy per claim across a run, and compare runs on a scoreboard.

Build: a dispatcher and a scoreboard

  1. Build the dispatcher first with a one-second stand-in for the claim agent, and time it at caps of 1, 5 and 25.
  2. Simulate a 429 from the model provider and add a RetryPolicy that retries it with backoff.
  3. Swap in the real claim agent and run the harder claims as a swarm of 5 and of 25, traced and scored.
  4. In the product, start a dispatch from the dashboard with N agents (default 3), record each claim's cost and active time, and add a Scoreboard page for evaluation runs.

Cost: the same per claim as before; a swarm only changes how long you wait. Free models are limited to about 20 requests a minute, so keep N small on them.

Teams, swarms and fleets

TermMeaningExample
TeamA few agents collaborating on one taskA coding agent's planner, implementer and reviewer
SwarmMany agents working in parallel on independent pieces25 claim agents, one claim each
FleetEvery agent a business runs, managed togetherWayfarer's claim agent, copilot and improver

Claims are independent, so a swarm is the right shape: no agent needs to talk to another, and the coordinator doesn't need to be a model at all. A dispatcher in plain code is cheaper, faster and more predictable than an LLM deciding who works next.

A dispatcher in LangGraph

Send starts one work_claim per claim, each with its own input. The operator.add reducer collects every worker's result into one list. max_concurrency caps how many run at the same time; the rest wait their turn.

What really limits a swarm

  • Rate limits. Providers return HTTP 429 when you send too many requests a minute. A retry policy with exponential backoff absorbs short bursts; a cap below the limit avoids them.
  • Shared resources. Every claim agent opens database connections for its records and checkpoints. A small hosted Postgres allows only a handful of pooled connections (Supabase's small tiers allow about 15), and agents queue for them. Twenty-five agents can be barely faster than ten.
  • The slowest claim. With enough agents, a run takes about as long as its slowest claim, not the sum.
  • Retries and money. A retried worker re-runs its claim. That's safe only because each claim keeps its own durable thread and the payment step is idempotent.

Measure every claim

Record each claim's model cost (from token usage) and active time (excluding time waiting for a person). Then an evaluation is just a dispatch over a copy of the evaluation or held-out claims, and a Scoreboard page can compare runs: accuracy, cost of mistakes, cost per claim, seconds per claim and the straight-through rate. That table is what the improver in Module 9 reads.

A claim waiting for sign-off doesn't block the swarm

Because each claim has its own thread, one paused for Rosa's sign-off simply stops; its worker finishes and the slot goes to the next claim. When she signs off, that claim resumes on its own, days later if need be.

Takeaways

  • Independent work suits a swarm with a coordinator in code, not a model.
  • Send fans out, a reducer collects, max_concurrency caps.
  • Rate limits, connection pools and the slowest item set the real speed; retry with backoff.
  • Durable threads and idempotent payments are what make parallel retries safe.

Check your understanding

Going from 10 to 25 agents barely speeds up the run. What's the most likely cause?

Concurrency only helps until the next shared limit; find it and size N to it.

Why is the dispatcher plain code rather than an LLM agent?

Use a model where judgment is needed, and code for the rest.

What makes it safe for RetryPolicy to re-run a claim agent that failed halfway?

Retries are only safe when repeating work can't repeat side effects.
