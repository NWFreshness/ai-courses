Evals and observability

Week 2 is about becoming the architect: making choices you can defend to a client with numbers. That starts with measuring the right thing. A model's answer can be plausible and wrong, and an accuracy score can hide which mistakes cost the business money. Today you build Wayfarer's evaluation, trace the agent's work, and use both to make your first architecture decision: should the model do arithmetic?

By the end of this module you can

  • Avoid three common architecture traps, and say when a second agent is justified.
  • Choose between direct measurement, a model judge and human review.
  • Score decisions with a confusion matrix, precision, recall, Cohen's kappa and a cost of mistakes.
  • Trace runs and compare experiments in Langfuse, and move business logic into code.

Build: an evaluation, and a payout tool

  1. Write 25 harder claims: several items with per-item limits, a deductible, and payments already made by another insurer.
  2. Create a free Langfuse Cloud project, trace one claim end to end, and load the claims with the handlers' answers as a dataset.
  3. Run a baseline experiment where the model works out the payout itself, scored on accuracy and cost of mistakes.
  4. Give the agent a calculate_payout tool written in Python, run the same experiment three times, and compare.

Cost: cents per experiment on a small model. Langfuse Cloud's free tier needs no card.

Three traps

  1. The "agent for X". Start from a business problem you can measure, and see how far you get without agents.
  2. Human-shaped teams. A "researcher", a "writer" and a "reviewer" sound sensible but multiply cost and failure points. Start with one agent; add another when it measurably helps.
  3. Plausible, not accurate. Model output reads well whether or not it's right. Only measurement tells you.

Good reasons to add an agent are specific: to isolate context (as work_claim does), for an independent check, to use a different model for a step, for parallel work, or to ring-fence permissions. And anything that's really business logic, a calculation, a rule, a limit, belongs in code, not in a prompt.

Scores that match the business

With three decisions there are nine combinations of the agent's answer and the handler's, a 3×3 confusion matrix. The diagonal is agreement. Off the diagonal, mistakes differ hugely in cost: a wrongful decline lets down a customer who was owed money, a wrongful approval pays money that wasn't owed, and a needless referral only costs a handler's time. Precision for "approve" asks how many of the agent's approvals were right; recall asks how many of the handlers' approvals the agent found.

Cohen's kappa corrects agreement for chance. If most claims deserve approval, "approve everything" agrees with the handlers most of the time, but its kappa is zero: it shows no skill at all. The cost of mistakes turns the same results into the number the client cares about, dollars.

Observability with Langfuse

A trace records one run: every model call, tool call and its timing and cost. A dataset holds inputs with expected outputs; an experiment runs a version of the agent over a dataset; scores attach results to each item, so experiments can be compared side by side.

Business logic belongs in code

Ask a model to add up six items, apply a per-item limit, subtract a deductible and another insurer's payment, and it will often be close and sometimes wrong. Write the calculation once, in Python with tests, and give it to the agent as a tool. The agent's job becomes deciding what is covered; the code decides how much.

Run each version at least three times: a run of 25 claims is noisy, and one good run proves little. When the reference course made this change on its own harder claims, wrong decisions or amounts fell by about three quarters across three runs.

Two different accuracies

The confusion matrix counts decisions only, so an approval with the wrong amount sits on the diagonal. Accuracy also checks the payout. Report both, and say which you mean.

Takeaways

  • Start from a measurable business problem and one agent; add agents for specific reasons.
  • Measure directly where you can, use judges for the rest, and calibrate with people.
  • A confusion matrix, kappa and a cost of mistakes say far more than one accuracy figure.
  • Trace runs, compare experiments over several runs, and put business logic in code.
