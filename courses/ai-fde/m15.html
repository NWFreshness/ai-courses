Capstone and handover

An engagement ends when the client can run the system without you. Today you add the last piece, a copilot that lets handlers drive the system in plain language, then hold the handover conversation: work the queue, review the claims that need a person, and answer the question the client asked on day two. Are the success criteria met? Then you tear everything down.

By the end of this module you can

  • Design a copilot for a client's staff that acts with their identity and asks before anything irreversible.
  • Check success criteria in code, against the targets agreed in discovery.
  • Run a handover, and tear a deployment down completely, with proof that it's gone.
  • Scope a capstone of your own that uses everything in the course.

Build: the copilot, the handover and the teardown

  1. Plan the copilot with your coding agent and have a second agent review the plan before you build.
  2. Build it as a hand-written LangGraph loop with tools for claims, customers, starting work and the context layer; a confirmation card before any payment; durable conversations; and a memory per handler.
  3. Deploy it on its own runtime beside the claim agent, signed in as the handler, never with the agent's key.
  4. Hold the handover as Rosa: work the queue with ten agents, ask why a claim needs her, send one back with a note, sign off another, and ask whether the success criteria are met.
  5. Tear everything down, and check by name, by an account-wide resource search, and by the budget.

The copilot

Handlers shouldn't need to learn a dashboard's every corner to ask "why does this claim need me?". A copilot in the sidebar answers questions and takes actions in plain language. Its design follows everything before it:

ConcernDesign
IdentityIt acts with the signed-in handler's own credentials, so permissions and the audit trail are theirs. It never holds the claim agent's API key.
Irreversible actionsBefore any payment, it shows a confirmation card with the claim, amount and reason, and waits (an interrupt() in a durable graph).
DurabilityEach conversation is a thread with checkpoints in Postgres, so it survives restarts and can continue tomorrow.
RuntimeIts own deployment and a session per conversation, separate from the claim agent.
MemoryA namespace per handler: Rosa's preferences and notes, not the customers'.
FactsQuestions like "are we meeting the targets?" are answered by code that computes the numbers, and the model explains them; it never estimates them.

Define the straight-through rate carefully: every claim not referred counts, including approvals waiting for sign-off, because the agent finished its part. Agree that definition with the client in discovery, not at handover.

The handover

A good handover is a working session, not a slide deck. The client's own expert drives the system while you watch: running the queue, reviewing what needs a person, overriding the agent, checking the numbers. Leave behind the documents they'll need without you: how to run it, monitor it, change its configuration, approve improvements, rotate its keys and switch it off; who owns what; and the evaluation they should rerun whenever anything changes.

Tear it down, and prove it

  • Remove the runtimes, gateway and policy engine, memories, functions, roles and the CLI's bootstrap stack.
  • Check three ways: list the project's resources by name; search the whole region with a resource explorer (a new account has some default resources, so it won't be empty); and watch the budget over the next day or two.
  • Deactivate the IAM user's access key when you're finished with the cloud account.

Your capstone

Build your own LangGraph solution to a business problem where an agent makes decisions within limits: a variation on Wayfarer, or something from your own work. It needs human sign-off above a limit, checkpoints in a database, a context layer, memory per user, and deployment to a runtime. Decide how you'll measure success before you build. Then find a real user for it: experience delivering to someone who depends on it is what turns these skills into the FDE role.

Takeaways

  • A copilot acts as the person using it, asks before irreversible actions, and computes facts in code.
  • Success criteria agreed in discovery are checked in code at handover.
  • Handover means the client runs it without you, with the documents to do so.
  • Teardown is part of the job, and it's checked, not assumed.

Check your understanding

Why does the copilot act with the handler's own sign-in instead of the claim agent's API key?

Acting on someone's behalf means acting with their permissions and audit trail.
