The solutions architect

Week 3 is about the part of the job that isn't code: running an engagement with a client from discovery to handover, deciding how much autonomy each action gets, answering the risk team's questions, and setting up the cloud account the system will live in. Today has no new agent, and it may be the module that matters most in a real engagement.

By the end of this module you can

  • Run an agent project through five phases, with governance, evals and change management throughout.
  • Sort candidate use cases in discovery and write a discovery note with a baseline and a target.
  • Decide autonomy per action as a risk decision, and choose where an agent runs.
  • Answer responsible-AI, privacy and accountability questions, and set up a safe cloud account.

Build: a discovery note and an AWS account

  1. Write a one-page discovery note for Wayfarer, or for a problem at your own work: the problem, who has it, the baseline today, the target, how you'll measure it, and the risks.
  2. Fill in an autonomy decision for each action the claim agent can take.
  3. Open an AWS account with a root user, put MFA on root, and choose us-east-1 for the course.
  4. Create a monthly budget of $10 with alerts (excluding credits and refunds), an IAM user with only the permissions the course needs, and its access key; run aws configure and check from Python.

Cost: nothing today. AWS has no hard spending cap, so the budget alerts matter. The free route uses Render instead.

Through every phase run four threads: clear ownership, governance (tollgates where the client decides whether to continue), evaluations, and change management for the people whose work changes.

Discovery

Sort candidate use cases into three kinds. Automation does an existing task with less human effort (deciding routine claims). Acceleration helps people do their work faster (a copilot for handlers). Differentiation does something new that sets the business apart (instant decisions at the airport gate). For each, ask: is the value measurable and worth it; is the data there and good enough; and what happens when the agent is wrong? A discovery note answers those questions on one page, with a baseline (how it works and performs today) and a target agreed with the client.

Architecture and where agents run

A typical enterprise shape: the agent reaches business systems through gateways (which hold security rules), integrations with systems of record, and a context layer of business knowledge (Module 12). Start with the simplest version that meets the need, and expect to redesign within a year as tools and models change. An agent can run on your own infrastructure (containers, functions), on a managed agent runtime such as Amazon Bedrock AgentCore, or inside a model lab's own hosted agent product. The choice trades control against effort.

Autonomy is a risk decision, per action

"How autonomous is the agent?" is the wrong question. Ask it per action: reading a claim is harmless, approving a $40 taxi is low risk, paying $4,000 isn't, and changing a customer's policy is out of scope. Each action gets a level, from fully automatic, through a person approving, to people only. Treat agents like any other software asset: inventoried, owned, versioned, reviewed and retired properly.

Responsible AI, privacy and handover

Expect a risk and compliance review. Organize your answers around common responsible-AI pillars: fairness, reliability and safety, privacy and security, inclusiveness, transparency and accountability. On privacy, know exactly where data goes: which model provider, under which terms, whether prompts are retained or used for training (paying doesn't by itself guarantee they aren't; check the product's terms and settings), and in which region. On accountability, name who owns each decision the system makes. Plan for handover from the start: the client must be able to run, monitor, change and switch off the system without you. And plan for adoption: a system the handlers don't trust won't be used, however accurate.

A cloud account that can't surprise you

Account setup traps

Use the sign-up path that creates a full account with a root user, so you can choose the region and create IAM users; some newer simplified sign-ups restrict regions and IAM. Put MFA on root and never use it day to day. Exclude credits and refunds from the budget, or it will show zero spend and never alert. Use one region for everything, and check the region selector first when something seems to be missing in the console.

Takeaways

  • Five phases, with ownership, governance, evals and change management throughout.
  • Discovery sorts use cases and ends in a one-page note with a baseline and a target.
  • Decide autonomy per action by risk; treat agents as software assets.
  • Prepare privacy, accountability, handover and adoption answers early; set up cloud accounts with budgets and least privilege.

Check your understanding

A copilot that drafts replies for handlers to edit and send is which kind of use case?

It speeds up people's work rather than replacing a task or creating a new offering.

The client asks "how autonomous will it be?". What's the best answer?

Autonomy is decided per action, from automatic to people only.

Why exclude credits from the AWS budget?

You want to see what you're using, not the net bill after credits.
