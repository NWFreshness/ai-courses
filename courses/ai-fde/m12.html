Security, guardrails and gateways

Claims are written by customers, and a customer can write anything, including instructions aimed at the agent. Before Wayfarer goes live, the agent needs defenses in layers: a check on what comes in, a key on the API it calls, and a gateway that enforces payment limits whatever the model decides. Today you build each layer, deploy the app to the cloud, and test them against a claim designed to fool the agent.

By the end of this module you can

  • Name the three kinds of agent risk and the lethal trifecta.
  • Screen inputs for prompt injection with a keyword check and a model check, and measure false alarms.
  • Protect the agent's API with a key, and deploy the app to a serverless function.
  • Put a gateway in front of the agent's tools with a policy that limits payments.

Build: defenses in layers

  1. Write a claim that hides an instruction to approve an expensive watch. See which models fall for it.
  2. Add a keyword check, then a model check with structured output, as the first step of the claim graph; a flagged claim is referred to a handler. Test both on rewordings and on 25 ordinary claims for false alarms.
  3. Require an API key (X-API-Key) on the agent's routes, describe them in an OpenAPI document, and package the app for AWS Lambda with Mangum.
  4. Deploy the app with a Function URL, create an AgentCore Gateway with the app as a target and the key held by the gateway, and add a policy forbidding payments over $1,000: first log-only, then enforced.

Cost: cents on AWS (Lambda and the gateway charge per use), plus the model calls. The free route deploys the app on Render, without the gateway.

Three kinds of risk

  • What the agent can do where it runs: its files, network and credentials.
  • What it can do through its APIs: every tool is a permission. Paying claims is a permission to move money.
  • Prompt injection: instructions and data share one channel, the context window, so text in a claim can act like an instruction.

Simon Willison's lethal trifecta names the dangerous combination: access to private data, exposure to untrusted content, and a way to communicate externally. Wayfarer's agent reads untrusted claims and can move money, so it gets layered guardrails: input checks before the model sees content, output checks on what it produces, action limits enforced outside the model, and a constrained environment.

Screening the claim

A keyword list catches the obvious attempt and misses the first rewording. A model check catches rewordings because it reads for intent, but it costs a call and can raise false alarms on ordinary claims (a customer writing "please approve quickly" isn't an attack). Measure both: catches on attack variants, and false alarms on normal claims. No set of checks makes an agent bulletproof, which is why the next layers don't depend on the model at all.

Keys, functions and gateways

The agent calls the app's API with a key, sent as X-API-Key and checked by the backend. To run the app on AWS Lambda, wrap the FastAPI app with Mangum (handler = Mangum(app)) and give the function a URL. Note that a Function URL is public: the key protects the agent's routes but doesn't stop anyone reaching the function, so the routes themselves must check it.

Gateways come in three kinds: API gateways in front of services, MCP gateways in front of tools, and model gateways in front of providers. The products change monthly, so stay light. AgentCore Gateway is an MCP gateway: it reads an OpenAPI document and turns each operation into an MCP tool, adds the target's credentials from AgentCore Identity so the agent never holds the key, and checks every call against Cedar policies.

With a policy engine attached, a call is refused unless something permits it, and a forbid always beats a permit. Start the engine in log-only mode to see what it would refuse, then enforce it. Now the $1,000 rule holds in three places: the backend, the gateway, and the prompt, in decreasing order of how much you rely on it.

The key lives in one place

The agent's API key belongs to the agent (or the gateway, which adds it for the agent) and the backend that checks it. It never goes in a frontend setting, where anyone with a browser can read it. Generate it with python -c "import secrets; print(secrets.token_hex(32))" and keep it in .env and the cloud's secret store.

Takeaways

  • Risks come from the environment, the APIs and injected instructions; the trifecta is the dangerous combination.
  • Screen inputs with cheap and model checks, and measure catches and false alarms.
  • Keys on every route; gateways add credentials and enforce policy outside the model.
  • Put critical limits in several layers, and rely most on the ones a model can't argue with.

Check your understanding

The model check flags 3 of 25 ordinary claims. What's the cost of that?

False alarms have a business cost; measure them alongside catches.

Why does the Cedar forbid on payments over $1,000 matter if the backend already refuses them?

Independent layers fail independently, and gateway logs show you who tried what.

With both a permit for all tools and a forbid for large payments, a $1,500 payment is…

In Cedar, an applicable forbid overrides any permit.

Exercise: attack, then defend

Write three new injection attempts that get past your model check, then improve the check until it catches them without adding false alarms on the 25 ordinary claims. Add an output check (an after_model hook) that refers any approval whose payout exceeds the amount claimed, and a Cedar policy that refuses approvals over $5,000.
