The enterprise context layer

So far the agent's knowledge lives in files you copied into the project. In a real business, that knowledge belongs to teams: Product owns the plans, Claims Operations owns the rules, Legal owns the wording, and each changes on its own schedule. Today you give that knowledge a home of its own, a context layer the agent reads as tools, with every fact traceable to an owner, plus a memory of each customer.

By the end of this module you can

  • Describe the four parts of an enterprise context layer and where each kind of data lives.
  • Serve business knowledge to agents as an MCP server, with provenance on every file.
  • Route an agent's tools through a gateway, and record the full context behind each decision.
  • Give an agent per-customer memory with extraction strategies and namespaces.

Build: a context server and a customer memory

  1. Split Wayfarer's knowledge into files, each with a header naming its source system, owner and review date: plans, claim rules, the glossary, the data dictionary, reference data, the wording and the manual.
  2. Serve them as a small MCP server with lookup and search tools, deploy it as a second function behind IAM auth, and add it to the gateway as a target.
  3. Have every decision store a full record: the lookups made, the sections relied on, and the memory used. Show it on the claim page as "Context used".
  4. Create an AgentCore Memory with two strategies, facts about each customer and a summary of each claim, and give the agent a tool to search the current customer's memories.

Cost: cents on AWS. The free route runs the context server on your laptop and keeps customer memory in Postgres.

From context engineering to a context layer

Context engineering decides what a model sees for one task. An enterprise context layer makes the business's knowledge available to every agent, governed like any other data. It has four parts:

PartQuestionWayfarer examples
MeaningWhat does the data mean?The glossary ("deductible", "trip interruption"), the data dictionary
PracticeHow is the work done?Claim rules (60-day filing window, third claim in 12 months is referred), the claims manual
PermissionWhat may this agent see and do?Read the rules, never the answer key; pay only under the limit
ProvenanceWhere did it come from, and is it current?Source system, owner and review date on every file

Most of this is long-standing data governance and master data management, now with agents as consumers. The FDE's job is usually to connect what exists, not to invent it.

Where each kind of data lives

  • The gateway holds the security team's rules: who may call what, with which credentials.
  • The context layer holds knowledge the business teams own, read through tools.
  • Memory holds the agent's own notes, such as what it has learned about each customer.
  • The database is the system of record (claims, policies, payments), reached only through the app's API.

A context server

Memory per customer

A managed memory such as AgentCore Memory stores the raw conversation as events and extracts long-term records in the background using strategies: semantic (facts), summary (a summary per session), user preference, and episodic. Namespaces decide where each record lands and who can find it, using the actor and session IDs you pass.

The customer ID in that tool comes from the claim the agent is working, set by your code, never chosen by the model. That's what keeps one customer's history out of another's decision.

This hands-on simulator needs JavaScript.

Memory is eventually consistent

Extraction runs in the background, usually within a couple of minutes, so a memory written by one claim may not be searchable by the next one immediately. The agent also decides for itself whether to search, so a claim may not use memory at all; the "Context used" panel shows whether it did.

Takeaways

  • A context layer covers meaning, practice, permission and provenance, governed like any data.
  • Gateway for security rules, context layer for business knowledge, memory for the agent's notes, database for records.
  • Serve knowledge as tools with provenance on every answer, and record the context behind each decision.
  • Scope memory by namespace from code, never by the model's choice.

Check your understanding

Where should the rule "a third claim within 12 months is referred" live?

It's business practice owned by a team, so it belongs in the context layer with its owner and review date.

Why is the customer ID in search_memory set by code rather than passed by the model?

Scoping data access is a permission decision, made in code.

What does provenance on each context file let you do?

When a decision is challenged, you need to know where its facts came from.
