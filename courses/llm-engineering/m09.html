Week 8 · Module 8 of 9 · capstone finale

The Price Is Right: an autonomous multi-agent system

Week 8 assembles everything into one product. A fleet of agents scans deal feeds, estimates each item's true value with your fine-tuned model, a RAG-backed frontier model and a neural network, decides which deals are worth your attention, and pushes the best one to your phone. It runs on a timer behind a Gradio dashboard.

By the end of this week you can

  • Deploy a fine-tuned open model as a serverless GPU service and call it from Python.
  • Combine several pricing models into an ensemble, including RAG over hundreds of thousands of products.
  • Use structured outputs to turn messy feed text into typed objects.
  • Build a planning agent that decides which tools to call, with memory so it doesn't repeat itself.

Project: The Price Is Right, part 3

  1. Deploy your Week 7 model as a GPU service on Modal and write a specialist agent that calls it.
  2. Embed your training products into Chroma and write a frontier agent that prices an item using its five most similar products as context.
  3. Write an ensemble agent that combines the specialist, the frontier agent and a neural network, and score it with your Tester.
  4. Write a scanner agent that reads deal RSS feeds and returns structured deals, and a messaging agent that sends a push notification.
  5. Write a planning agent that uses three tools (scan, estimate, notify) with a memory file so it never repeats a deal; put it on a timer behind a Gradio dashboard.

Cost: Modal's free monthly credits are usually enough if containers sleep; keeping one warm uses credits continuously. Frontier calls are cents. Pushover has a free trial, then a small one-time fee.

The architecture

"Agent" in this project mostly means a focused component with one responsibility and a log line when it acts, not a free-roaming AI. Only the planning agent makes open-ended decisions, and even it has exactly three tools. That's a useful design habit: keep autonomy where it adds value and make everything else ordinary, testable code.

Serving your model with Modal

Your Week 7 adapter needs a GPU to run. Modal lets you decorate a Python function or class, say which container image and GPU it needs, and run it in the cloud: once ("ephemeral") with modal run, or as a persistent service with modal deploy. The pricer service loads the 4-bit base Llama 3.2 3B, applies your adapter from the Hugging Face Hub at a pinned revision, and exposes a price method; the specialist agent simply calls it.

Modal secrets have a name, a key and a value

This confuses many people. Your code looks up a secret named huggingface-secret, which must contain a key HF_TOKEN whose value is your token. A mismatch in any of the three fails at container start. Also expect the first run to take several minutes while the image builds, and a cold start of around half a minute after the service sleeps; setting MIN_CONTAINERS = 1 keeps it warm at a continuous cost.

RAG for prices, and an ensemble

Week 6 showed frontier models price well from world knowledge. Give them more to go on: embed hundreds of thousands of training products with the local all-MiniLM-L6-v2 model into Chroma, and for each new item retrieve the five most similar products with their known prices and include them in the prompt. Then the ensemble agent combines three estimates with fixed weights: 0.8 for the RAG frontier agent, 0.1 each for the specialist and the neural network.

The final step is small (from $30.19 to $29.90), which is typical of ensembles: they mostly smooth out each model's worst misses. The bigger lesson is the jump from Week 6's zero-shot frontier model to the RAG version. Showing a model similar, labeled examples at inference time is a powerful alternative to training it.

Scanning and messaging

The scanner agent reads deal RSS feeds, then asks a model to pick the most promising deals and rewrite each into a clean description with a clear price. Instead of asking for JSON in the prompt, as in Week 1, it uses structured outputs: you pass a Pydantic model as response_format, and the API guarantees the reply matches that schema.

The messaging agent sends a push notification through Pushover with the deal, its price, the estimated value and the link. You add a user key and an app token to .env.

The planning agent

Build the workflow first with three pretend functions that return canned data, to test the logic cheaply, then swap in the real ones. The autonomous planning agent gives a model three tools and a goal, and lets it decide the order:

  • scan_the_internet_for_bargains calls the scanner agent.
  • estimate_true_value calls the ensemble agent for one description.
  • notify_user_of_deal calls the messaging agent.

It's the same tool-calling loop you wrote in Week 2, with more consequential tools. The deal agent framework wraps it: it loads the list of deals already surfaced from memory.json, passes it to the planner so the same deal isn't sent twice, records the new one, and sets up logging so you can watch each agent work.

The product

Finish with a Gradio dashboard on gr.Blocks: a table of surfaced deals, live agent logs, and a plot of the product vector space, with a gr.Timer that runs the framework periodically. Run it, leave it open, and deals arrive on your phone. For a next step, try rebuilding the planner with an agent framework and MCP servers; that's where the Agentic AI course picks up.

Look at it as a harness engineer

This agent reads untrusted text (deal feeds that anyone can publish to) and has an outbound channel (notifications to you). It doesn't hold private data, so Simon Willison's "lethal trifecta" isn't complete, but add a tool that reads your email or accounts and it would be. The memory file is its only state, so a crash mid-run is harmless but two copies running at once could notify you twice. Harness Engineering Module 8 and Module 9 cover both.

Takeaways

  • Serve fine-tuned open models on serverless GPUs with Modal; pin the adapter revision and mind cold starts.
  • RAG with labeled examples sharply improved frontier-model pricing; an ensemble smooths the rest.
  • Structured outputs turn model replies into typed objects you can trust in code.
  • Give autonomy to one planner with a few well-defined tools; keep the other agents as focused, testable components with memory around them.

Check your understanding

What did the frontier agent add in Week 8 that cut its error from about $45 to about $30?

Retrieval-augmented pricing: comparable labeled examples at inference time.

Why does the scanner agent use response_format with a Pydantic model?

Structured outputs replace "please reply in JSON" with a schema the API enforces.

The Modal container fails to start with a Hugging Face authentication error. What do you check first?

Name, key and value all have to match what the code looks up; it's a common trap.

Exercise: point it at something you care about

Keep the architecture and swap the domain. Ideas: a scanner over vendor security-advisory feeds that estimates "how much does this affect me" from your inventory and notifies you of the top one; or a scanner over job postings that scores fit against your résumé. Keep the planner to three tools, add a memory file, and write down which inputs are untrusted before you add any tool that reads private data.
