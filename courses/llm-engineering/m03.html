Two money-and-quality levers

Reasoning effort

Reasoning models can "think" before answering, spending extra tokens to work through a problem. That's inference-time scaling: spending more compute per question rather than training a bigger model. Try a probability puzzle such as "I toss two coins and one is heads; what's the chance the other is tails?" with reasoning off and on; small models often get it wrong without reasoning. More effort costs tokens and time, so set it per task: none or low for summarizing, higher for puzzles, math and code.

Prompt caching

If many requests share a long identical prefix (a system prompt, a document, a codebase), providers can cache it and charge much less for the repeat. Try it: attach a long public-domain text, such as the whole of Hamlet, to a question, send it twice, and compare cached tokens and cost. OpenAI and Gemini cache automatically above a size threshold; Anthropic needs explicit cache markers. The rule that follows: put the stable, shared content first and the changing question last. Harness Engineering has a full section on designing for the cache (Module 4).

Gradio: an interface in a few lines

Gradio wraps a Python function in a web UI. You give it a function and describe the inputs and outputs; it renders the page and calls your function. If the function is a generator that yields successively longer strings, the output streams.

launch(share=True) gives a temporary public link, and auth=("user", "password") adds a simple login. There are three styles of Gradio UI: gr.Interface for a function, gr.ChatInterface for chat, and gr.Blocks when you want to lay out components and wire events yourself.

A chatbot is a history-passing loop

With gr.ChatInterface, your function receives the new message and the history so far. Your job is to turn that into the messages list the API wants: system prompt, then the history, then the new message. That's Week 1's "illusion of memory" made concrete.

The system prompt doesn't have to be fixed. A shop assistant could append extra instructions only when the customer mentions a product that's on offer. Injecting context based on what the user said is the seed of retrieval in Week 5.

Tools: letting the model ask your code for help

The model can't look up a ticket price. But you can describe a function to it, and it can reply with "please call get_ticket_price with destination_city="Paris"" instead of an answer. Your code runs the function and sends the result back, and the model writes the final reply.

The while loop, rather than a single if, lets the model chain several lookups. That loop is the heart of every agent you'll build, and Harness Engineering Module 2 takes it apart in detail.

Going multimodal

Add an artist(city) function that calls an image-generation model for a picture of the destination, and a talker(text) that turns the reply into speech with a text-to-speech model, both through the same client (client.images.generate and client.audio.speech.create). Have the tool handler also return which cities were looked up, so the UI knows what to draw. Then lay out chat, image and audio side by side with gr.Blocks.

Tool results the model can't use

Return something the model can read and act on, like "London: $799" or "No price found for Lisbon", not None or a raw exception. And always send back exactly one result per tool call ID, or the next API call will fail.

Takeaways

  • Pick the access layer per job: native SDK for full features, compatible endpoints for one shape, LiteLLM for light abstraction and cost tracking.
  • Spend reasoning effort only where it pays; put shared content first so prompt caching can help.
  • Gradio turns functions into apps; yielding text streams it.
  • A chatbot is history in, reply out. Tools are a loop: the model asks, your code runs, the result goes back.
