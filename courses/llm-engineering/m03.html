Many models, real interfaces, and tools

Week 2 widens the lens to every major provider, puts a user interface on your code with Gradio, builds a chatbot that keeps its history, and then gives it tools: functions it can ask your code to run. It closes with an airline assistant that looks up prices in a database, draws pictures and speaks.

By the end of this week you can

  • Call several providers through their native SDKs, compatible endpoints, routers, and LiteLLM.
  • Explain reasoning effort and prompt caching, and when each saves you money or improves answers.
  • Build Gradio interfaces and a chatbot that passes history correctly.
  • Implement tool calling end to end, including several tool calls in one turn.

Four ways to reach a model

ApproachExampleTrade-off
Native SDKanthropic.Anthropic().messages.create(...)Full feature set for that provider; a different shape for each

RouterOpenRouter: one key, hundreds of modelsConvenient for comparing; a middleman in the path
Abstraction libraryLiteLLM (light), LangChain (heavy)LiteLLM gives one call plus token and cost reporting; LangChain adds a large framework you may not need yet

The author's stated favorite is LiteLLM, because it's light: one completion() call with a provider/model string, and it reports token counts and cost for each response.

Two money-and-quality levers

Reasoning effort

Reasoning models can "think" before answering, spending extra tokens to work through a problem. Day 1 contrasts training-time scaling (bigger models trained on more data) with inference-time scaling (letting a model spend more compute per question), using a coin puzzle that a model gets wrong with reasoning off and right with a little reasoning on. More effort means more tokens, cost and latency, so set it per task: low or none for summarizing, higher for puzzles, math and code.

Prompt caching

If many requests share a long identical prefix (a system prompt, a document, a codebase), providers can cache it and charge much less for the repeat. Day 1 demonstrates by asking a question about Hamlet with the whole play attached, twice, and printing cached tokens and cost. OpenAI and Gemini cache automatically above a size threshold; Anthropic needs explicit cache markers, and Gemini supports both styles. The rule that follows: put the stable, shared content first and the changing question last. The Harness Engineering course has a whole section on designing for the cache (Module 4).

Gradio: an interface in a few lines

Gradio wraps a Python function in a web UI. You give it a function and describe the inputs and outputs; it renders the page and calls your function. If the function is a generator that yields successively longer strings, the output streams.

Day 2 also shows share=True for a temporary public link, auth=(user, password) for a simple login, and forcing dark mode. Day 5 introduces the three styles of Gradio UI: gr.Interface for a function, gr.ChatInterface for chat, and gr.Blocks when you want to lay out components and wire events yourself.

A chatbot is a history-passing loop

With gr.ChatInterface, your function receives the new message and the history so far. Your job is to turn that into the messages list the API wants: system prompt, then the history, then the new message. That's Week 1's "illusion of memory" made concrete.

Day 3's clothes-store assistant shows a small but powerful idea: the system prompt doesn't have to be fixed. When the user mentions belts, the code appends extra instructions for that turn. Injecting context based on what the user said is the seed of retrieval in Week 5.

Tools: letting the model ask your code for help

The model can't look up a ticket price. But you can describe a function to it, and it can reply with "please call get_ticket_price with destination_city="Paris"" instead of an answer. Your code runs the function and sends the result back, and the model writes the final reply.

The notebook starts with a single tool call, then handles several in one turn, then moves the prices into SQLite with a set_ticket_price helper. Using a while loop rather than a single if, as above, lets the model chain lookups. That loop is the heart of every agent you'll build, and it's exactly what Harness Engineering Module 2 takes apart in detail.

Going multimodal

Day 5 adds an artist function that generates a picture of the destination city and a talker that turns the reply into speech, both through the same OpenAI client. The tool handler now also returns which cities were looked up, so the UI knows what to draw. A custom gr.Blocks layout ties chat, image and audio together.

Tool results the model can't use

Return something the model can read and act on: "London: $799" or "No price found for Lisbon; ask the customer to pick another city", not None or a raw exception. And always send back one result per tool call ID, or the next API call will fail.

Takeaways

  • Pick the access layer per job: native SDK for full features, compatible endpoints for one shape, LiteLLM for light abstraction and cost tracking.
  • Spend reasoning effort only where it pays; put shared content first so prompt caching can help.
  • Gradio turns functions into apps; yielding text streams it.
  • A chatbot is history in, reply out. Tools are a loop: the model asks, your code runs, the result goes back.

Check your understanding

The model responds with finish_reason == "tool_calls". What must your code do before calling the model again?

The next call needs the model's request and every matching result in the history, or it can't continue the conversation.

You ask 50 questions about the same 200-page manual. How should you order the prompt to benefit from caching?

Caches match on identical prefixes. A stable prefix followed by the changing question gets the discount.

Which Gradio building block fits a custom layout with a chat panel, an image and an audio player?

gr.Blocks lets you place components and wire events yourself, which is what Day 5 does.

Exercise: an assistant for something you know

Build a FlightAI-style assistant for a domain you work in, with two tools backed by SQLite: one to look something up and one to change something. Make the change tool ask for confirmation first by returning "Confirm: …" for the model to relay, and only apply it on a second call that includes confirmed=true. Log every tool call to the console so you can watch the loop.
