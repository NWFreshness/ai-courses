Frontier models and your first LLM product

This week you make your first API call, turn it into a web-page summarizer, and finish with a brochure writer that chains several model calls. Along the way the mystery comes out of what an LLM API is: an HTTP endpoint that takes a list of messages and returns the most likely continuation.

By the end of this week you can

  • Call a chat model with system and user messages, and explain what each role does.
  • Point the same client code at OpenAI, Gemini, or a local Ollama model.
  • Explain tokens, and why every call to an LLM is stateless.
  • Chain two model calls, ask for JSON, and stream a long answer back.

Project: summarizer, then brochure writer

  1. Write fetch_text(url) with requests and BeautifulSoup: return the page title and visible text (drop scripts, styles and navigation), trimmed to about 10,000 characters.
  2. Write summarize(url): one model call with a system prompt and the page text. Try three different sites.
  3. Switch the client to Ollama and compare the summaries.
  4. Count the tokens in a request with tiktoken, and prove to yourself that the model forgets earlier calls.
  5. Build the brochure writer: one call picks the useful links from a company's home page as JSON; your code fetches them; a second call writes a brochure and streams it.

Cost: cents, or free on Ollama.

The Chat Completions shape

Almost every provider now accepts the same request: a model name and a list of messages, each with a role. The system message sets the job and the tone. User messages are what you ask. Assistant messages are what the model said earlier. The response is the model's prediction of the next assistant message.

The client library is a thin wrapper

You could send the same request with requests.post to the provider's /v1/chat/completions URL and a bearer token, and parse the JSON yourself. The openai package doesn't contain a model; it builds that HTTP request and parses the reply. That matters because so many providers expose OpenAI-compatible endpoints: the same client works against them if you change base_url and the key.

Running locally trades capability for privacy and price: nothing leaves your machine and nothing is billed, but a 3-billion-parameter model is far less capable than a frontier one. Avoid pulling 70-billion-parameter models onto a laptop; they won't fit.

Tokens

Models don't read characters or words. They read tokens: chunks of text from a fixed vocabulary, often a common word, a piece of a word, or punctuation with its leading space. Tokens are what you pay for, what fills the context window, and why models are oddly bad at counting letters: the letters are hidden inside tokens.

The illusion of memory

Tell a model your name in one call, ask for it in the next, and it has no idea. Every call is stateless. A chat product creates the impression of memory by resending the whole conversation every time: the system message, then every user and assistant message so far, then the new one. That's why long chats cost more and eventually run out of room, and it's the root of almost everything later in this course: chat UIs (Week 2), retrieval (Week 5) and agent memory (Week 8) are all ways of choosing what goes into that list.

From one call to a small pipeline

Three techniques make the brochure writer work:

  • Ask for JSON, with an example. The link-picker's system prompt shows one example of the exact JSON it wants back, such as {"links": [{"type": "about page", "url": "https://…/about"}]}, and asks for full URLs rather than relative ones. One example is one-shot prompting; several is few-shot. A stricter technique, structured outputs, arrives in Week 8. Many providers also accept response_format={"type": "json_object"} to force valid JSON.
  • Let code do what code is good at. The model decides which links matter; plain Python fetches them. Don't ask a model to do what a function can.
  • Stream long answers. With stream=True you receive the reply as small chunks and can show text as it arrives.

In a notebook, show can be display(Markdown(reply), display_id=…) with update_display; in a terminal, print each chunk with end="".

Pages that come back empty

A simple scraper reads the HTML the server sends. Sites built with client-side JavaScript send almost no text, and sites behind bot protection may return a 403. For those, a browser-automation tool such as Playwright or Selenium renders the page first.

Takeaways

  • A chat API takes a list of role-tagged messages and returns the next assistant message.
  • The client library is just HTTP; OpenAI-compatible endpoints let one client reach many providers, including local Ollama.
  • Models see tokens, and every call is stateless: memory is whatever you put in the messages.
  • Split work into small calls with clear jobs, ask for JSON with an example, and stream long output.

Check your understanding

You send "Hi, I'm Dana" in one API call and "What's my name?" in a second. Why doesn't the model know?

The model only sees what's in the current request. Chat apps resend the whole conversation to create the impression of memory.

To switch your summarizer from OpenAI to a local Llama model, what changes?

Ollama exposes an OpenAI-compatible endpoint at localhost:11434/v1, so the same code works.

Why does the brochure writer use two model calls instead of one?

Splitting the work makes each step easier for the model and lets ordinary code handle fetching, which a model can't do on its own.
