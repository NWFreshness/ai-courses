Retrieval-augmented generation, built and measured

Week 5 builds an expert assistant for Insurellm, a fictional insurance-tech company, that answers questions from the company's own documents. By the end of this week you can

  • Explain RAG as "find relevant context, put it in the prompt", and build the simplest version.
  • Chunk documents, embed them, store them in Chroma and retrieve by similarity.
  • Evaluate retrieval with MRR, nDCG and keyword coverage, and answers with an LLM judge.
  • Apply advanced techniques (LLM chunking, document rewriting, query rewriting, reranking) and measure whether they help.

Project: an expert assistant for one company

  1. Assemble a knowledge base of 30–80 Markdown documents in folders by type (company, products, employees, contracts). Use documents you own, or have a model generate a consistent fictional company; the reference course uses one called Insurellm, and its sample documents are a good starting set.
  2. Build the crude version: if a question mentions a known name, paste that document into the prompt.
  3. Chunk, embed and store everything in Chroma; plot the vectors in 2D to check they cluster by type.
  4. Wire retrieval and a chat model into a Gradio chat assistant.
  5. Write a test set (aim for 50+ questions, with keywords and reference answers), measure retrieval and answers, then add LLM chunking, query rewriting and reranking one at a time and keep only what helps.

Cost: well under a dollar for embeddings and evaluation on a small knowledge base.

What RAG is

A model only knows what it was trained on plus what's in the prompt. RAG adds a step before generation: find the passages most relevant to the question and include them in the prompt, with an instruction to answer from them. The rawest form of the idea: if a question mentions an employee's name, paste that employee's file into the system prompt. It works for exact names and fails for anything phrased differently, which is the problem embeddings solve.

Chunks, embeddings and vector stores

  • Chunking splits documents into passages small enough to be specific and large enough to make sense on their own. The basic implementation uses LangChain's RecursiveCharacterTextSplitter with 500-character chunks overlapping by 200, so a fact that straddles a boundary still lands whole in at least one chunk.
  • An embedding model turns text into a vector so that passages with similar meaning end up close together. Good choices include OpenAI's text-embedding-3-large and the small, free, local all-MiniLM-L6-v2 from Hugging Face.
  • A vector store (Chroma here) saves the vectors with their text and metadata and finds the nearest ones to a query vector.

A t-SNE plot squashes the vectors into two or three dimensions so you can see them. Chunks from the same kind of document (employees, products, contracts, company pages) cluster together, which is a good visual check that the embeddings capture meaning.

LangChain can do the same with its retriever and chat-model objects, which both expose invoke(). Either way, RAG is less complicated than it's often made out to be. Making it good is the hard part, and that requires measuring it.

Measuring RAG

Start with a test set. Each test is a question with a reference answer, a category, and a few keywords that a relevant chunk should contain. The reference course's set has 150 questions, mostly direct facts plus temporal, spanning, comparative, numerical, relationship and holistic ones; copying that mix of categories shows you which kinds of question your pipeline gets wrong.

Retrieval metrics: did we find the right passages?

MetricQuestion it answersIn this repo
MRR (mean reciprocal rank)How high up is the first relevant result?1/rank of the first chunk containing each keyword, averaged
nDCGAre relevant results concentrated near the top?Binary relevance per keyword over the top 10, normalized against the ideal order
Keyword coverageWhat share of the needed facts appear at all?Percentage of keywords found in the retrieved chunks
Recall@KOf all relevant chunks, how many are in the top K?See the correction below

Recall versus hit rate

These two are often confused. The share of tests where some relevant context appeared is hit rate. Recall@K for one test is the number of relevant chunks in the top K divided by all relevant chunks for that test. The two are equal only when each test has exactly one relevant chunk.

Answer metrics: was the reply right?

Answers are graded by an LLM acting as judge, which compares the reply with the reference answer and returns scores for accuracy, completeness and relevance, plus written feedback, as structured output. Look at the feedback, not just the scores; it tells you whether a failure came from retrieval (the fact wasn't in the context) or generation (it was there and the model missed it).

Going pro

Now rebuild the pipeline natively, without a framework, for full control, and add techniques one at a time, evaluating each with the same tests.

  • LLM chunking. Instead of cutting every 500 characters, ask a model to split each document into sensible overlapping chunks, returned as structured output (a Pydantic Chunk model with a headline, a summary and the original text).
  • Document pre-processing. Storing the headline and summary alongside the text gives the embedding more to match against than raw prose.
  • Query rewriting. A model rewrites the user's question (using the conversation so far) into a better search query before retrieval.
  • Reranking. Retrieve generously (20 chunks), ask a model to order them by relevance to the question, and keep the best 10 for the prompt.

Every technique is a hypothesis

Each of these adds latency and cost. Keep one only if your evaluation numbers improve. That's the most transferable lesson of the week, and it's the same evaluate-then-change loop that Harness Engineering Module 10 builds for agents.

Fixing generation when retrieval is broken

If the right chunk never makes the top K, no prompt will rescue the answer. Check retrieval metrics first; tune chunking, embeddings and reranking there, and only then work on the answer prompt.

Takeaways

  • RAG means retrieving relevant passages and answering from them; the basic version is short.
  • Chunk with overlap, embed with one model for both documents and queries, store in a vector database.
  • Measure retrieval (MRR, nDCG, coverage, recall) separately from answers (an LLM judge against references).
  • LLM chunking, query rewriting and reranking are worth it only if the numbers say so.

Check your understanding

A test has four relevant chunks; three appear in your top 10. What's its Recall@10?

Recall@K is relevant chunks found in the top K divided by all relevant chunks: 3 / 4. "At least one was found" is hit rate.

Answers are wrong, and the judge's feedback says the needed fact wasn't in the context. Where do you work first?

The model can't use what it wasn't given. Fix retrieval, confirmed by retrieval metrics, before tuning generation.

Why retrieve 20 chunks and then rerank down to 10?

Retrieve wide for recall, then rerank for precision, so the prompt holds the most relevant passages.

Exercise: RAG over your own documents

Point the pipeline at 20–50 documents you actually use: runbooks, internal how-tos, product manuals. Write 25 test questions with keywords and reference answers, covering at least three categories. Measure the basic pipeline, then add one technique at a time (a different chunk size, query rewriting, reranking) and record the retrieval and answer scores after each. Keep only what helps.
