From prototype to production

The course ends with a working product on your laptop. Running something like it for other people, every day, is a different job. This module lists what a learning prototype deliberately leaves out, gives you a checklist for your own first project, and points to where each topic is covered in depth.

By the end of this module you can

  • Name the gaps between a prototype and a production LLM application.
  • Plan a portfolio project that uses at least three of the course's techniques.
  • Choose where to go next for agents, evaluation and reliability.

What a prototype leaves out (on purpose)

Learning projects optimize for learning: notebooks and global variables, everything in one process, keys in a local file, a human watching. None of that is wrong for a prototype. Here's what changes when it isn't one.

A first project worth showing

Pick a problem from your own work, where you know what a good answer looks like. A strong portfolio project combines at least three techniques from the course and has a measured result. Some shapes that work well:

  • A RAG assistant over documents you own (runbooks, manuals, policies) with a 30-question evaluation and before/after numbers for each improvement (Weeks 2, 5).
  • A structured-extraction pipeline that turns messy records into a clean dataset with batch calls, plus a small model or fine-tune that uses it (Weeks 6, 7).
  • A narrow agent with three tools that watches a feed and notifies you, with memory, logs and a written threat model (Weeks 2, 8).

Where to go next

  • Agents in depth. The Agentic AI course builds on Week 8 with agent frameworks (OpenAI Agents SDK, CrewAI, LangGraph and others) and MCP.
  • Reliability around agents. The Harness Engineering course covers the loop, tools, context, verification, sandboxing, durability and evaluation that turn a working agent into one you'd run unattended.
  • Share what you built. Publish the project with its README and results table; a measured result is the most convincing thing in a portfolio.

Takeaways

  • Prototypes leave out evaluation suites, tracing, failure handling, security, cost control and deployment on purpose; production needs all of them.
  • The best next project is narrow, from your own work, measured against a baseline, and documented.
  • The habit that carries over from every week: define success, measure it, change one thing, measure again.

Check your understanding

A provider retires the model your app uses. What does a production setup do that a prototype doesn't?

Model changes are like any other change: measured before shipping, against the same tests.

What makes a portfolio project convincing to someone reviewing it?

Measured improvement over a baseline shows engineering judgment, which is what reviewers look for.
