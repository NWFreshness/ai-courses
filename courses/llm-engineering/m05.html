Choosing the right model: a code-generation race

How do you pick a model when there are hundreds? Week 4's answer is to stop reading marketing and test models on your own task with a measurable outcome. The task: convert Python into fast C++ or Rust, compile it, run it, check the output matches, and time it.

By the end of this week you can

  • Narrow the field of models using cost, context size, licensing and public benchmarks.
  • Build a small benchmark of your own with an objective pass/fail and a score.
  • Prompt a model to generate code that compiles and produces identical output.
  • Explain why running generated code needs care, and how to contain it.

Project: the Python-to-C++ race

  1. Write two Python benchmark programs that print a result and their run time: an easy one (a numeric series, such as approximating π with a loop) and a harder one (for example, a maximum-subarray search over numbers from a seeded pseudo-random generator).
  2. Ask one model for the exact compile and run commands for your machine, giving it your OS, CPU and installed compilers.
  3. Write port(model, python) that asks for C++ only, then write the reply to main.cpp.
  4. Compile and run it in a sandbox (a container with no network), check the output matches Python's, and record the speedup.
  5. Race at least four models, including one open-weights model, on both programs. Put the converter behind a Gradio UI with a model dropdown.

Cost: cents to a dollar, depending on how many frontier models you race with high reasoning effort.

Narrowing the field

Before benchmarking, rule models in or out on the basics:

QuestionWhy it matters
Open or closed? What license?Whether you can self-host, fine-tune, and use it commercially
Size and hardwareWhether it fits on your GPU or needs a hosted endpoint
Context windowWhether your input (code, documents, history) fits
Price and speedCost per million input and output tokens; latency and throughput
Knowledge cutoffWhether it knows recent libraries and APIs
Reasoning supportWhether you can trade more thinking for better answers

Public benchmarks and leaderboards help narrow further, with caveats: scores can be gamed or leak into training data, and a benchmark rarely matches your task exactly. Use them to make a shortlist, not a decision.

Your own benchmark beats anyone else's

The code-conversion task is a good benchmark because the outcome is objective. The C++ either compiles or it doesn't; its output either matches Python's or it doesn't; and its runtime is a number. That's the same principle you'll use for RAG in Week 5 and pricing in Week 6: define success as something you can measure, then compare models on it.

Prompting for code that compiles

Make the system prompt strict, for good reasons. Ask for only code (so the reply can be written straight to a file), output identical to the Python version, and attention to details that commonly break ports, such as integer overflow. The user prompt carries the Python source. A separate first call, given a report of your OS, CPU and compilers, can tell you the right compile and run commands for your machine.

Then compile with optimization flags, run, and compare. For the frontier models, speedups over Python typically run into the hundreds or thousands. In the reference course's published runs, the open-weights GPT-OSS 120B produced a program about 110,000 times faster than the Python on the harder problem, while a small local coder model (Qwen 2.5 Coder) failed outright. Your numbers will differ by machine and model version, which is the point: run it yourself.

You are running code a model wrote

The quick way to run this project is to exec() Python and compile and run generated C++ directly on your computer. For a known toy program that's tolerable. For anything else it isn't: generated code can delete files, hang, or exhaust memory, and if the input came from someone else, it can be steered to do so. Run generated code in a container or a VM with no network and no access to your files, with a timeout. Harness Engineering Module 8 covers how.

What to take from the results

  • Correctness before speed. A fast program with different output scores zero.
  • Harder problems separate models. On the easy benchmark most frontier models do well; the harder one reorders the field.
  • Reasoning effort matters for code. Turn it up for models that support it.
  • Open models are viable for some jobs. Some open-weights models compete with closed ones on this task; small local ones often don't.

Takeaways

  • Shortlist on license, size, context, price, cutoff and reasoning; use leaderboards to narrow, not to decide.
  • Build a benchmark with an objective score on your actual task, and compare models on it.
  • Prompt for exactly the output format you need, and still clean up what comes back.
  • Run generated code only in an isolated, time-limited environment.

Check your understanding

A model's C++ runs 900× faster than the Python but prints a different number. How should it score?

A conversion that changes behavior is a failure. Correctness is the gate; speed is the score among correct answers.

Why are public leaderboards a starting point rather than the answer?

Use them to build a shortlist, then decide with a benchmark on your own task.

Which is the safest way to run code a model generated from user input?

Isolation and limits hold regardless of what the code tries to do. Asking the model doesn't.

Exercise: a benchmark for your own work

Pick a task you'd actually use a model for, with a checkable answer: converting a config format, writing a regex that must match a list of examples, or writing a SQL query that must return known rows. Write ten test cases, run three models (one frontier, one cheap, one local), and record pass rate, cost and time in a table. Keep the table; you'll extend this idea with proper evals later.
